## [Unreleased]

### Security

<!-- issue-66: retention-wording -->
- Уточнена формулировка bounded retention после #46: штатный API
  (`keystore.get_all_keys()`) немедленно ограничен `[active, retired]`, а
  физический `fernet_key_retired` сокращается до одного ключа только
  после успешной явной ротации с завершённым prune (#66, #46, ADR-46).
- Снято чрезмерное обещание, что компрометация keyring раскрывает
  максимум два ключа: до physical prune legacy- или partial-failure
  история остаётся в backend и доступна субъекту с прямым доступом.
- Зафиксировано фактическое поведение verification failure: смена active
  не откатывается, физический retired-entry содержит два ключа, текущее
  и предыдущее поколения читаются, безопасный retry приводит к bounded
  physical state (#66).


- `prepare` при `overwrite=False` проверяет полный набор целевых артефактов —
  `prompt.txt`, `route.json` и `manifest.json` — одной проверкой до первой
  операции записи (#48, аудит #42, ADR-48). Ранее одиночный существующий
  `manifest.json` не блокировал запуск и заменялся атомарной публикацией #45,
  то есть ранее валидный артефакт терялся без предупреждения. При отказе
  preflight существующие файлы сохраняются побайтово, отсутствующие не
  создаются, `save_manifest` и `_write_atomic` не вызываются, временные файлы
  не появляются.
- Проверка коллизий остаётся best-effort: между preflight и публикацией
  сохраняется race, строгий no-clobber при конкурентном писателе не
  заявляется (ADR-48). Каталог по целевому имени блокирует запуск, broken
  symlink — нет; semantics `Path.exists()` едины для трёх артефактов.
- Защита `RestoreContext.discard` от поддельного и изменённого контекста
  (#43, ADR-34). Удаление рабочего каталога выполняется только после
  подтверждения владения: доверенная база из конфигурации фасада, canonical
  containment по компонентам пути, отказ следовать symlink и junction, маркер
  владения `.pgw-owner` с совпадающим handle, HMAC-SHA256 на секрете владения
  и повторная сверка идентичности каталога перед удалением. При любом отказе
  проверки не удаляется ничего.
- Проверка владения не обращается к хранилищу ключей: освобождение ресурсов
  остаётся возможным после `pgw key rotate` и `pgw key delete`.
- Перед рекурсивным удалением рабочий каталог отцепляется от исходного имени,
  а identity закреплённого корневого объекта и маркер владения проверяются
  повторно (#43, дополнение ADR-34).
- Рекурсивное удаление не начинается от неподтверждённого непустого дерева:
  корневой workspace закрепляется descriptor (Linux) или handle (Windows),
  обход начинается от закреплённого объекта, а имена детей разрешаются
  относительно закреплённого родителя в принятой модели угроз. Если
  закрепление нельзя доказать, операция завершается fail closed; допустим
  остаточный каталог `.pgw-quarantine-*` (#52, #54, дополнения ADR-34).
  Гарантия не распространяется на same-identity процесс с прямым доступом
  внутрь workspace. Ранее подмена quarantine-имени перед началом обхода могла
  привести к удалению подставленного каталога.
- Секрет владения на границе удаления сравнивается с секретом, на котором
  проверен код аутентичности контекста, через constant-time comparison; ранее
  в ветви без `dir_fd` проверялось только наличие маркера с совпадающим
  `handle` (#52).
- Временный файл `.pgw_restore_*.tmp` с восстановленным plaintext удаляется при
  любом неуспешном исходе `write_restored`, включая отказ `os.replace` после
  успешной записи (#44, аудит #42). Ранее cleanup охватывал только запись, и
  при отказе публикации plaintext оставался на диске рядом с destination.
  Имя временного файла сохраняется до конца операции, удаление выполняется в
  `finally` и покрывает подготовку каталога, `mkstemp`, `fdopen`, запись,
  закрытие потока и `replace`; после успешного `replace` уже опубликованный
  destination не удаляется. Дескриптор закрывается до `unlink`, поэтому cleanup
  работает и на Windows. Если сама операция `unlink` отклонена ОС, временный
  файл может остаться: первичная ошибка записи не маскируется и не подменяется,
  абсолютная гарантия удаления не заявляется.
- При отказе `os.fdopen` сырой файловый дескриптор временного файла закрывается
  явно и больше не утекает до конца процесса (#44).
- `manifest.json` публикуется атомарной заменой: полное содержимое
  сериализуется, пишется во временный файл `.manifest-*.tmp` в каталоге
  назначения и публикуется одним `os.replace` (#45, аудит #42, ADR-45).
  Ранее `save_manifest` выполнял прямой `Path.write_text`, поэтому наблюдатель
  мог увидеть пустой или частично записанный манифест, а отказ записи
  уничтожал ранее валидный файл. Теперь при отказе сериализации, `mkstemp`,
  `fdopen`, записи, закрытия потока или `replace` существующий манифест
  сохраняется побайтово, а при отсутствующем адресате новый файл не
  появляется. При отказе `os.fdopen` сырой дескриптор закрывается явно.
  Дескриптор закрывается до `unlink`, поэтому cleanup работает и на Windows.
  Если сама операция `unlink` отклонена ОС, временный файл может остаться:
  первичная ошибка не маскируется, абсолютная гарантия удаления не
  заявляется. `fsync` файла и каталога не выполняется — crash durability не
  обещается; атомарна публикация одного файла, а не всего набора артефактов
  `prepare`.
- Ограничена глубина хранения retired-ключей: `keystore.get_all_keys()` возвращает не более двух ключей `[active, retired]` без дублей, а `rotate_key()` после подтверждённой смены активного ключа удаляет историю глубже одного поколения (#46, #42, ADR-46). До исправления после трёх ротаций были доступны четыре ключа и расшифровывались манифесты всех поколений, что расширяло blast radius компрометации keyring. Манифесты старше одного retired поколения больше не читаются штатным API; ротация является destructive operation для глубокой истории, backup или export key material не предусмотрены. Чтение, `pgw key status`, restore и импорт модуля key material не удаляют.
### Changed

- CLI `prepare`: сообщение об отказе при `overwrite=False` перечисляет теперь
  и `manifest.json` в детерминированном порядке `prompt.txt, route.json,
  manifest.json` (#48). Форма фразы, префикс `BLOCKED: `, пустой stdout и код
  завершения 3 не изменились; `--overwrite`, argparse и семантика
  `routing_cfg.overwrite` не затронуты.
- Порядок публикации артефактов #45 не изменён единым preflight и закрыт
  тестами: `manifest.json` → `manifest_sha256` → `prompt.txt` → `route.json`.
- **Ломающее изменение.** `CONTEXT_FORMAT_VERSION` изменён с `1` на `2`.
  Контексты восстановления, сериализованные версией `0.4.0`, больше не
  принимаются: `RestoreContext.from_token` поднимает `RestoreError`.
  Обоснование и политика совместимости — ADR-34.
- Рабочий каталог операции содержит служебный файл `.pgw-owner` с правами
  только для владельца.
- Порядок публикации артефактов `prepare` не изменён и закрыт
  характеризационными тестами: `manifest.json` → `manifest_sha256` →
  `prompt.txt` → `route.json`. Завершающим маркером набора остаётся
  `route.json`, который связывает набор через `manifest_sha256` (#45).
- Опубликованный `manifest.json` создаётся из временного файла `mkstemp`
  с правами только для владельца; последующий `chmod` в `pipeline.py`
  сохранён, наблюдаемые права не ослаблены (#45).
- `rotate_key()` выполняет три записи в keyring в фиксированном порядке: carry предыдущего активного ключа в retired, запись нового активного ключа, verification чтением и prune истории (#46, ADR-46). Неподтверждённая смена активного ключа или незавершённый prune дают `KeystoreError` и код 4 без key material в сообщении; активный ключ не теряется, повторный `pgw key rotate` приводит keyring к bounded-состоянию. Состав CLI-команд, коды возврата, схема манифеста и версия пакета не изменены.

### Добавлено (Э8 — ротация ключей и MultiFernet)

- `crypto.py` — расширен поддержкой MultiFernet:
  - `encrypt_multi(plaintext, keys)` — шифрует первым ключом списка (`keys[0]`);
  - `decrypt_multi(ciphertext, keys)` — перебирает ключи по очереди до первого успешного расшифрования;
  - при исчерпании всех ключей поднимает `DecryptionError`.

- `keystore.py` — расширен поддержкой ротации:
  - `rotate_key()` — создаёт новый active-ключ, сохраняет текущий как retired; сначала записывает retired, затем active (атомарность в смысле keystore);
  - `get_all_keys()` — возвращает `[active_key, retired_key]`; новый ключ первым гарантирует шифрование новых манифестов активным ключом;
  - `delete_key()` — удаляет active и retired ключи; операция необратима.

- Команда `pgw key` с тремя подкомандами:
  - `pgw key create` — создать новый активный ключ (ошибка, если ключ уже существует);
  - `pgw key rotate` — ротировать ключ (старый сохраняется как retired, новый становится active);
  - `pgw key delete` — удалить ключ с предупреждением о необратимости; требует `--yes` в интерактивном режиме.

- `restore_text` теперь использует `get_all_keys()` + `decrypt_multi`:
  - манифесты, созданные до последней ротации, читаются без ручных действий (ADR-23);
  - новые манифесты шифруются активным ключом.

- Разведён код возврата 5 для строгого токенного отказа:
  - `RestoreStrictError` — отдельный класс исключения (не наследник `RestoreError`);
  - CLI отлавливает `RestoreStrictError` явно и завершается с кодом 5;
  - ошибки конфигурации/целостности по-прежнему возвращают код 3.

- `tests/test_key_rotation.py` — тесты ротации и жизненного цикла ключей:
  - после `rotate_key()` активный ключ новый; старый не расшифрует новый шифртекст;
  - манифест, созданный до ротации, читается через `get_all_keys()` + `decrypt_multi` (ADR-23);
  - нарушение порядка ключей в MultiFernet обнаруживается при шифровании;
  - прерывание `rotate_key` до завершения второй записи оставляет active без изменений;
  - удаление ключа делает данные нечитаемыми (`KeyNotFoundError`, `DecryptionError`);
  - полный цикл `create → prepare → restore → rotate → restore` старого манифеста;
  - коды 3, 4, 5 различимы между собой.

### Добавлено (Э7 — восстановление текста)

- `restore.py` — сквозное восстановление исходных значений в ответе LLM:
  - загрузка и проверка `route.json`;
  - выбор `manifest_path` с поддержкой явного `--manifest`;
  - разрешение относительного пути от каталога `route.json`;
  - проверка целостности до обращения к keyring и расшифровки;
  - загрузка и расшифровка `manifest.json`;
  - подстановка всех известных токенов;
  - формирование отчёта без исходных и восстановленных значений.

- Команда `pgw restore`:
  - ответ LLM читается из файла или stdin;
  - `--route` задаёт обязательный путь к `route.json`;
  - `--manifest` переопределяет путь к манифесту;
  - `--out` записывает восстановленный текст в файл;
  - `--overwrite` разрешает замену существующего результата;
  - `--lenient` явно включает мягкий режим;
  - без `--out` восстановленный текст выводится в stdout;
  - служебный отчёт без plaintext выводится отдельно.

- Классификация токенов в недоверенном ответе LLM:
  - известные токены восстанавливаются;
  - неизвестные токены вызывают отказ в строгом режиме;
  - искажённые кандидаты вызывают отказ в строгом режиме;
  - пропавшие токены включаются в отчёт без произвольной подстановки;
  - дублированные известные токены заменяются во всех вхождениях;
  - регистр токенов не нормализуется автоматически.

- Строгий режим включён по умолчанию. Мягкий режим доступен только через
  явный флаг `--lenient`.

- Атомарная запись восстановленного результата через временный файл в
  каталоге назначения и `os.replace`.

- Добавлены модели результата восстановления и безопасного отчёта без
  расшифрованных значений.

- Добавлены тесты Э7:
  - точный и Unicode round-trip `prepare → restore`;
  - чтение ответа LLM из stdin;
  - строгий отказ для неизвестных и искажённых токенов;
  - мягкий режим только по явному флагу;
  - отчёт о пропавших и дублированных токенах;
  - поддержка `route.json` версий `1.0` и `1.1`;
  - отказ для неизвестной версии;
  - проверка целостности до keyring и расшифровки;
  - обнаружение подменённого или повреждённого манифеста;
  - разрешение относительного `manifest_path`;
  - читаемые ошибки чужого или отсутствующего ключа;
  - отсутствие plaintext в служебном отчёте;
  - отсутствие выходного файла при ошибке;
  - защита существующего результата без `--overwrite`.

### Добавлено (целостность артефактов)

- `route.json` версии `1.1` связывается с финальным `manifest.json` через
  поле `manifest_sha256`, содержащее SHA-256 всех байтов файла.
- Добавлена публичная функция
  `verify_manifest_integrity(route_data: dict, manifest_path: Path) -> None`.
- Версия `route.json` `"1.0"` поддерживается без контрольной суммы для
  обратной совместимости.
- Версия `"1.1"` требует корректного `manifest_sha256`.
- Неизвестные версии, отсутствующий файл и несовпадение суммы отклоняются
  через `ConfigurationError`.

### Изменено

- Контрольная сумма вычисляется после атомарной записи `manifest.json` на
  финальный путь; затем атомарно записывается связанный `route.json`.
- `verify_manifest_integrity` вызывается для фактически выбранного
  манифеста до keyring, загрузки и расшифровки.
- Код возврата 3 также используется для ошибки целостности и строгого
  отказа `restore`; ошибка keyring по-прежнему возвращает код 4.
- Документация обновлена для Э7:
  - `README.md` описывает команду и цикл `prepare → restore`;
  - `docs/ARCHITECTURE.md` описывает поток восстановления;
  - `docs/SECURITY.md` рассматривает ответ LLM как недоверенный вход;
  - `docs/DECISIONS.md` фиксирует архитектурные решения Э7.
- Уточнено, что SHA-256 обнаруживает рассинхронизацию и повреждение, но без
  подписи не обеспечивает аутентичность и не защищает от согласованной
  подмены обоих файлов.

### Изменено (Э8)

- `restore_text` использует `get_all_keys()` + `decrypt_multi` вместо
  одиночного `get_key()` — обратная совместимость манифестов после ротации (ADR-23).
- Код возврата 5 выделен для строгого токенного отказа (`RestoreStrictError`);
  код 3 остаётся для ошибок конфигурации и целостности (ADR-21).
- `docs/DECISIONS.md` обновлён: добавлены ADR-21…ADR-25; ADR-06 переведён
  в статус «действует» (MultiFernet реализован).
