# ADR-274 amendment: continuation and final delivery boundaries

Дата: 2026-10-01. Corrective scope #274; epic #248.

Task completion does not authorize replacing an active task checkpoint. The
epic continuation has its own owner-only cursor and process lock. It can
advance only from a terminal task checkpoint, recomputes the structural queue,
and creates a separate successor checkpoint. Repository, epic, roadmap and
pinned policy stay unchanged. A successor uses a freshly validated plan under
the same mandate; its base equals the previous verified merge SHA. Unknown
preparation is reconciled, not blindly repeated. Old checkpoints remain
available for audit and reconciliation. A cursor is not a mandate.

Final writes are a separate driver, never task delivery with a fabricated
task/PR. Its closed identity binds repository, epic, policy, roadmap ref/SHA,
main base SHA, real PR and merge SHA as applicable. Operations are explicitly
allowlisted as `create_roadmap_pr`, `merge_roadmap_pr`, `close_epic` and
`update_epic`. None is implied by task grants or another operation.

The driver obtains gates from a trusted provider, not request/checkpoint
booleans. FINAL_GATE requires the existing ADR-256 assessment, actual full
local gate, independent cumulative-diff review, verified lesson/negative
prompt evidence, no open structural children and SHA-bound owner confirmation
of the real final demo. Merge additionally requires exact same-repository PR
head/base identity and its five successful checks. Closing/updating the epic
requires the actual main merge SHA's separate five successful checks.

Every imminent write rechecks fresh mandate lifecycle/digest, live identity
and actual consumed iteration counts. In mandate `3.0`, starting another task
at the task limit is forbidden; finalization at exactly the consumed limit
remains allowed because it does not start a task. Exceeding the limit still
blocks finalization; legacy lifecycle semantics are unchanged. Gates are
revalidated too. A private ledger records intent before the write. Unknown outcomes
are reconciled read-only, never retried without proof of NOT_APPLIED. No force
push, admin merge, branch deletion, credential fallback or owner confirmation
generation is introduced. The protected roadmap branch is retained.

Successor preparation treats its scoped fetch as a potentially applied local
mutation before invoking it. Expiry, revocation or failure after that point
preserves the outer pending task. An absent task branch/checkpoint does not
prove that tracking refs or objects were untouched; without the complete
preparation receipt reconciliation returns UNKNOWN and requires owner action,
rather than clearing the intent and repeating preparation.

Post-merge ancestry proof may explicitly import only the freshly confirmed
merge object from the scoped repository, without tags, FETCH_HEAD or ref
updates. Authority and separate post-merge CI are checked before this import;
remote identity is checked again afterward. Missing/changed facts still block.
Finalization likewise imports the exact approved roadmap object and advances
the non-checked-out local roadmap only by ancestry-checked compare-and-swap,
including after the last task when no successor is prepared.
On final resume after main merge, the advanced main SHA is accepted only from
the exact previously bound roadmap PR's fresh MERGED/mergeCommit facts.
Unrelated main movement still blocks; no new final approval is fabricated.
Local imports, successor branch creation, roadmap compare-and-swap and
worktree switches re-read approval/lifecycle/identity immediately before the
mutation, not only before preceding network reads. Expiry/revocation during
fetch forbids the next mutation. If a prior local preparation mutation has
already occurred, a blocked continuation preserves unknown-preparation intent.
Successor guards also refresh the scoped remote main/roadmap SHAs, actual local
repository identity, source branch/HEAD, clean worktree, expected local roadmap
and (after fetch) tracking refs. Task branch absence is required before creation;
its exact base is required before switch. Remote or local drift during fetch,
planner preflight or handover preparation prevents the next mutation without
clearing pending preparation. Authority is refreshed after these read checks.

A valid consumer-demo plan establishes readiness, not execution. Applicable
task closure additionally requires a closed owner-only `demo-completion.json`
receipt binding the exact plan digest, repository/epic/task, baseline/roadmap
SHAs and current owner identity, with `completed_by_owner: true`. It contains
no input/output and is never generated by the model or runtime. Missing or
stale completion blocks closure; justified DEMO_NOT_APPLICABLE remains valid.

Runtime-config `2.0` adds exactly one `epic_command`, subject to the same
owner-only script/argv/PID-namespace validation as phase commands. Legacy
config `1.0` stays a one-task runtime. The concrete entry's `epic_resume`
uses a closed `epic-runtime.json` and separately approved plan recipes. It
binds only the recipes' base/default SHA fields to fresh GitHub refs; criteria,
scope, paths, policy and budgets are not generated or expanded from issue
text. Each successor passes the existing planner and handover validation.
Scoped fetch imports only main/roadmap objects and remote-tracking refs; the
local roadmap ref advances only by proven fast-forward and compare-and-swap,
never while checked out. Branch preparation/switch uncertainty preserves the
outer intent for reconciliation.

Final approval may be absent (`approved_final_digest: null`) while tasks run.
FINAL_GATE then stops with FINAL_DEMO_UNCONFIRMED. Only the owner supplies
the SHA-bound confirmation/digest once the real final SHA and demo are known.
The driver executes full gate and negative lesson tests on the actual tree,
reviews the immutable cumulative commit diff, and refuses oversized review
data rather than silently truncating it. Cached evidence binds policy, main,
roadmap and actual tested tree. It does not substitute owner confirmation.
The concrete controller has an explicit 1,000,000-character input bound,
including the frozen policy bundle; the executor retains its existing bound.
Oversized requests still fail closed and are never silently truncated.
PR descriptions are generated only from validated identity and trusted
primary gate artifacts. Runtime Python is captured beside the genuine gate;
support metadata comes from the exact published Git revision. Both task and
roadmap PRs report local checks separately from pending PR/post-merge CI,
absent GitHub Review, scoped compatibility limitations and remaining owner
actions. Raw logs, prompts, private paths and demo input/output are excluded.
Reporting and other argument preparation occur before the concrete transport's
final trusted write guard. That guard refreshes identity/gates and then mandate
approval/lifecycle immediately before launching the write command. Intent
persistence is followed by another authority check; denial retains intent
for read-only reconciliation. No model/request can supply or replace this guard.

Synthetic end-to-end tests establish code paths, not production-pilot success.
Installing the reviewed policy, issuing/approving a new scoped mandate,
running the real-input demo and confirming its result remain owner actions.
