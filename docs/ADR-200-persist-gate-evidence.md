# ADR-200: персистентность gate evidence, вердикта и идентичности snapshot

## Статус

Принято. Задача #200, epic #179.

## Контекст

Запись прогона агентного оркестратора не сохраняла доказательную часть
прогона. Публичная запись содержала только `run_id`, `started`, `status`,
`machine_code`, счётчики вызовов, `repair_iterations`, `findings`,
`failures`, `verdicts` и `terminal`. Приватная retrospective со
`schema_version` `1.0` содержала агрегатные счётчики и длительность.

В обеих записях отсутствовали:

- `gate_evidence` целиком, включая профиль, его версию, полноту, статус,
  machine code, ожидаемые и фактически выполненные проверки;
- вердикт контроллера, `review_basis`, `escalation_reason` и blocking
  findings;
- идентичность trusted snapshot: `base_sha`, `snapshot_commit`,
  `tree_hash`, `diff_sha256`, `snapshot_method`, `provenance_complete` и
  результат проверки неизменности дерева;
- фактическая длительность прогона и по-ролевые длительности.

Из-за этого прохождение полного профиля gate доказывалось только косвенно,
через достижимость machine code и наличие вызова контроллера. Такое
доказательство зависит от порядка вызовов в коде, а не от содержимого
записи, поэтому прогон не является воспроизводимым доказательством.

Приватная retrospective хранится вне рабочего дерева репозитория, поэтому
её содержимое не проверяется ни `detect-secrets` в pre-commit, ни
`tools/check_secrets_baseline.py`. Публичный каталог записей прогона
копируется вместе с pilot-окружением и является наименее защищённым из двух
хранилищ. Оба факта прямо влияют на решение.

## Решение

### Р1. Blocking findings сохраняются только как redacted-выжимка

Полный текст blocking findings не сохраняется ни в публичной записи
прогона, ни в приватной retrospective. Текст вердикта контроллера является
выводом языковой модели и штатно содержит фрагменты diff, содержимое
изменённых файлов, пути и потенциально секреты или персональные данные.

Каждый blocking finding сохраняется в приватной retrospective как
структурированная запись:

- `severity` из фиксированного перечня;
- `category` или стабильный `code` из фиксированного перечня;
- `location` с путём относительно корня репозитория и, при наличии,
  диапазоном строк;
- `summary` ограниченной длины, прошедший ту же нормализацию алфавита и
  ту же границу длины, что применяются к сводкам в `tools/agent_gate.py`;
- `check_id`, если finding относится к конкретной проверке;
- `finding_fingerprint` как SHA-256 нормализованного исходного текста;
- `redaction.applied` и `redaction.version`.

`finding_fingerprint` обеспечивает корреляцию одного и того же finding
между прогонами, дедупликацию и осмысленную работу существующего поля
`false_positives` без хранения исходного текста.

Если finding невозможно безопасно нормализовать, сохраняется запись с
кодом `FINDING_REDACTION_FAILED`, без исходного материала. Факт наличия
blocking finding при этом не теряется. Persistence является fail-closed
относительно приватности.

Отдельный редактор текста для findings не вводится. Используются
существующие ограничения длины и алфавита из `tools/agent_gate.py`, а
нормализация путей выполняется через существующую подстановку метки
рабочего каталога.

### Р2. Evidence разделяется на два слоя из единой redacted-структуры

Граница между слоями проходит по природе данных, а не по важности:
детерминированный факт против суждения.

Публичная запись прогона содержит только величины, вычисленные
инструментами:

- идентичность snapshot: `base_sha`, `snapshot_commit`, `tree_hash`,
  `diff_sha256`, `snapshot_method`, `provenance_complete` и результат
  проверки неизменности дерева;
- сводку gate: профиль, версию профиля, полноту, статус профиля, machine
  code, перечень ожидаемых и фактически выполненных проверок;
- по каждой проверке — имя, статус и код завершения;
- фактическую суммарную длительность прогона.

Приватная retrospective содержит полный redacted пакет:

- весь redacted `gate_evidence`, включая длительности отдельных проверок и
  разобранные метрики с нормализованными путями;
- redacted вердикт: `verdict`, `review_basis`, `escalation_reason` и
  структурированные blocking findings по правилу Р1;
- те же поля идентичности snapshot, чтобы приватная запись оставалась
  самодостаточной;
- по-ролевые длительности.

Публичный stdout `RunResult` не расширяется.

### Р3. Единая точка редактирования и whitelist публичной проекции

Оба слоя строятся из одного redacted-объекта. Публичная проекция
реализуется как явный whitelist полей, а не как приватная запись за
вычетом отдельных полей. Whitelist не протекает при добавлении новых полей
в evidence, тогда как исключающий список протекает всегда.

### Р4. Версионирование схем независимо

`schema_version` приватной записи повышается, новые поля являются
необязательными, а записи `1.0` продолжают читаться без ошибок. Публичная
запись получает собственный идентификатор версии схемы и не переиспользует
версию схемы evidence из `tools/agent_gate.py`: это разные сущности с
разным темпом изменений.

### Р5. Единственный источник идентичности snapshot

Значения идентичности snapshot берутся из той реализации, которая
фактически формирует `gate_evidence`. Второй источник этих значений не
создаётся. Публикация расходящихся значений `tree_hash` из двух кодовых
путей дала бы запись, которая выглядит доказательством целостности, не
являясь им.

## Что не сохраняется ни в одном слое

- Сырой stdout и stderr языковой модели.
- Prompts и рассуждения модели.
- Полный текст blocking findings.
- Учётные данные и персональные данные.
- Путь каталога журналов.
- Абсолютные домашние и временные пути.
- Содержимое изменённых файлов рабочего дерева.

## Рассмотренные и отклонённые альтернативы

| Альтернатива | Причина отклонения |
| --- | --- |
| Полный текст findings в приватной записи | Является сырым выводом модели, создаёт канал утечки в хранилище вне проверки secret scanning, делает privacy-тест формальным |
| Полный текст findings под отдельным флагом | Опциональный fail-open в приватном контуре противоречит принятой fail-closed политике и создаёт два класса записей |
| Только число findings без структуры | Не позволяет отличить отдельные блокеры и определить их расположение |
| Вся evidence только в приватной retrospective | Публичная запись остаётся невоспроизводимым отчётом, доказательство исчезает вместе с локальным состоянием, критерий доказуемости из записи не выполняется |
| Вердикт и `review_basis` в публичной записи | Являются суждением модели, а не измерением; повышают поверхность раскрытия наименее защищённого хранилища |
| Длительности отдельных проверок в публичной записи | Побочный канал о составе тестов и оборудовании, источник недетерминизма записи |

## Последствия

Прохождение полного профиля gate и неизменность проверенного дерева
доказываются непосредственно из публичной записи прогона, без вывода по
достижимости machine code. Evidence сохраняется и при неуспешном, и при
неполном gate, когда контроллер не вызывался. Вердикт сохраняется и для
эскалации, и для прохождения с замечаниями.

Канонические схемы, семантика machine codes и коды завершения процесса `0`
и `20` не изменяются. Writable-scope enforcement остаётся предметом
отдельной задачи.
