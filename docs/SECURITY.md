# Модель угроз и политика безопасности

Документ описывает модель угроз Privacy Gateway, что попадает на диск, как обращаться с ключом и как сообщать об уязвимостях.

## От чего защищает

Privacy Gateway снижает риск **случайной** передачи следующих категорий данных во внешнюю языковую модель:

- ПДн: email-адреса, номера телефонов, IPv4 и IPv6, имена (через словарь)
- Пути к файлам и ресурсам (UNC, Windows, POSIX)
- Секреты по ключевым словам: `password=`, `api_key=`, `token=`, строки подключения, PEM-заголовки
- Высокоэнтропийные строки длиной ≥ 16 символов (порог Шеннона 3.0)
- URL-эндпоинты, денежные суммы, даты в распространённых форматах

Все исходные значения шифруются Fernet (AES-128-CBC + HMAC-SHA256) локально и хранятся только в зашифрованном виде. Открытых данных в манифесте и в выводе инструмента нет.

## От чего **не** защищает

- **Многострочные секреты** — токены/ключи, разбитые по нескольким строкам
- **Нестандартные форматы секретов** — пароли/ключи без keyword-паттернов
- **Косвенную идентификацию** — комбинация «должность + город + дата рождения» даже после токенизации может идентифицировать человека
- **Семантические атаки** — передача обезличенного, но достаточно контекстного текста провайдеру LLM
- **Намеренные утечки** — внутренний злоумышленник с доступом к keyring
- **Атаки на инфраструктуру** — компрометация системы до или после обработки
- **Юридическую защиту** — инструмент не является средством соответствия требованиям GDPR, 152-ФЗ или иных нормативов

## Что попадает на диск

| Файл | Содержимое | Чувствительность |
|------|-----------|------------------|
| `prompt.txt` (каталог задаёт пользователь) | Токенизированный текст без исходных значений | Низкая |
| `route.json` (тот же каталог) | Метаданные запуска: счётчики токенов, timestamp, source_ref | Низкая |
| `manifest.json` (тот же каталог) | token, entity_type, fingerprint, encrypted_value (hex) | Средняя — без ключа бесполезен |
| Системный keyring | Fernet-ключ (latin-1) | Высокая — должен быть защищён ОС |

**Что НЕ попадает на диск:** исходные значения в открытом виде, ключ в файлах репозитория, исходный текст (если явно не сохранён пользователем).

**`manifest.json`** создаётся с правами `rw-------` (только владелец). На Windows `chmod` игнорируется — защита обеспечивается правами NTFS.

## Безопасность YAML-конфига маршрутизации  [Э6]

- Конфиг загружается **только** через `yaml.safe_load` (см. ADR-10).
- Неизвестные ключи на верхнем уровне и в секции `rules` — немедленная `ConfigurationError`.
- Конфиг **не может отключить** проверку секретов: пересечение `tokenize` и `block_unconditionally` запрещено (см. ADR-11).
- Отсутствие файла конфига — безопасные умолчания, не ошибка.

## Что не содержит route.json  [Э6]

`route.json` содержит только метаданные: `format_version`, `status`, `timestamp`, `source_ref`, путь к манифесту и счётчики токенов по типам.

**`route.json` не содержит:** исходных значений сущностей, Fernet-ключа, соли, расшифрованных фрагментов, полного пути к входному файлу сверх `source_ref`.

## Целостность пары артефактов

`route.json` версии `1.1` содержит поле `manifest_sha256` — SHA-256 всех байтов финального `manifest.json`. Проверка этого значения обеспечивает обнаружение рассинхронизации пары артефактов и повреждения файла манифеста.

Контрольная сумма вычисляется только после завершения атомарной записи `manifest.json` на его финальный путь. Затем `route.json`, содержащий полученную сумму, также записывается атомарно.

`manifest_sha256` не является защитой от целенаправленной подмены и не обеспечивает аутентичность файлов. Субъект, способный заменить одновременно `route.json` и `manifest.json`, может пересчитать SHA-256. Для криптографической аутентификации отдельных зашифрованных записей по-прежнему используется Fernet; новое поле связывает пару файлов целиком.

Версия `route.json` `"1.0"` поддерживается для обратной совместимости без проверки суммы. Версия `"1.1"` требует наличия корректного `manifest_sha256`; неизвестные версии, отсутствующий манифест и несовпадение суммы отклоняются с явной ошибкой без раскрытия содержимого манифеста.

## Обращение с ключом

- Ключ хранится в системном keyring: SecretService (Linux), macOS Keychain, Windows Credential Vault
- Ключ **никогда** не логируется, не помещается в `repr`/`str`, не записывается в файлы репозитория
- При компрометации ключа: 1) немедленно создать новый (`create_key()`), 2) уничтожить старые манифесты или перешифровать их
- Доступ к keyring определяется правами учётной записи ОС; Privacy Gateway не управляет правами доступа

## Ротация ключа

`MultiFernet` не реализован (отложен до Э8). При смене ключа старые манифесты становятся нечитаемыми (`DecryptionError`). Процедура ротации:

1. Загрузить манифест: `load_manifest(path, old_key)`
2. Пересохранить с новым ключом: `save_manifest(entries, path)` после повторного `build_manifest` с `new_key`

## Почему fail closed

Privacy Gateway использует принцип fail closed во всех точках неоднозначности:

- Небезопасный keyring backend → `KeystoreError` (не записывать ключ в plaintext)
- Повреждённый шифртекст → `DecryptionError` (не возвращать мусор)
- Остаточные PII в тексте → `BLOCKED` (не разрешать отправку)
- Неизвестный тип токена → `PENDING` (не разрешать автоматическую отправку)
- Неизвестный ключ в YAML-конфиге → `ConfigurationError` (не применять частичный конфиг)
- YAML с тегами выполнения кода → отклоняется `safe_load` до любой обработки

Цена ложной тревоги (ручная проверка) значительно ниже цены ложного OK (утечка ПДн во внешнюю LLM).

## Репозиторий

**Не добавляйте в репозиторий реальные данные.** В тестах и примерах используйте только синтетику:
- Email: `user@example.com`
- IPv4: `192.0.2.10`
- IPv6: `2001:db8::1`
- Телефон: `+7 900 000-00-00`

Примеры в markdown при срабатывании `detect-secrets` закрывать inline-pragma, не менять `.secrets.baseline`.
