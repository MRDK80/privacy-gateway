# ADR-81: единственный источник версии пакета

## Статус

Принято. Решение владельца от 2026-08-30 по итогам read-only этапа 0 issue #81.

- Issue: #81 `refactor: единый источник версии пакета`.
- Parent roadmap: #41.
- База: `main` `0114e8fa27dc759ce63eb9cc3380b2907580504f`.
- Наблюдаемая версия пакета остаётся `0.5.0`. Version bump, tag и Release в scope не входят.

Этот ADR предшествует любому production/config diff. Сам ADR ничего не реализует.

## Контекст

После #79 (PR #80) в репозитории остались два вручную синхронизируемых представления
версии:

- `pyproject.toml:7` — статическое `version = "0.5.0"` в таблице `[project]`;
- `src/privacy_gateway/__init__.py:38` — публичный `__version__ = "0.5.0"`.

Расхождение обнаруживает только `tests/test_cli.py::test_version_matches_distribution_metadata`
и только после установки дистрибутива. Каждый release требует двух согласованных правок.

Этап 0 установил границы задачи:

- CLI-флага `--version` в проекте нет; `git grep -n -- '--version'` по `src`, `tests`, `docs`,
  `README.md`, `CONTRIBUTING.md`, `AGENTS.md` находит только `python --version` в описании
  локального gate;
- версия пакета не сериализуется в артефакты: единственные чтения `__version__` — объявление
  в `__init__.py:38`, реэкспорт в `__all__` (`__init__.py:53`) и два теста
  (`tests/test_cli.py:29-30`, `tests/test_cli.py:34-36`);
- форматы `prompt.txt`, `route.json`, `manifest.json` и их версии от строки версии пакета
  не зависят;
- `[build-system] requires = ["setuptools>=70", "wheel"]`, backend `setuptools.build_meta`,
  `requires-python = ">=3.11"`.

## Решение

Canonical source версии — строковый литерал `__version__` в `src/privacy_gateway/__init__.py`.
Метаданные дистрибутива выводятся из него build backend'ом.

```toml
[project]
name = "privacy-gateway"
dynamic = ["version"]

[tool.setuptools.dynamic]
version = {attr = "privacy_gateway.__version__"}
```

```python
__version__ = "0.5.0"
```

Статическое поле `project.version` из `pyproject.toml` удаляется. Второго места, где версия
задаётся вручную, не остаётся.

## Обоснование

Решающим критерием выбран не размер release-правки, а требование: ни один режим импорта не
должен возвращать версию, не соответствующую импортированному коду. Версия читается из того
же модуля, который находится в `sys.modules`, поэтому разойтись с исполняемым кодом она
физически не может.

Дополнительно вариант сохраняет текущий import contract: `privacy_gateway` продолжает
импортироваться из исходного дерева без установленного дистрибутива, метаданные при импорте
не читаются, обращений к файловой системе в import-пути не добавляется.

Подход перечислен Python Packaging User Guide как валидный наравне с хранением версии в
`pyproject.toml`: версия задаётся в исходном коде, build-система извлекает её при сборке.

## Инварианты

Следующие условия нормативны и обязательны к тестовой защите:

1. `__version__` — простое присваивание строкового литерала, совместимое с `ast.literal_eval`.
   Вычисления, вызовы функций, конкатенация, переприсваивание и производные от импортов
   запрещены.
2. `__version__` остаётся публичным и присутствует в `__all__`.
3. `project.dynamic` содержит `version`; статическое `project.version` отсутствует.
4. Тихий fallback на литерал при отсутствии metadata не вводится ни в каком виде.

Основание инварианта 1: директива `attr` в setuptools сначала пытается прочитать значение
статически, разобрав AST модуля, и лишь при неудаче импортирует модуль через
`importlib.util.spec_from_file_location`. Импорт на этапе сборки в документации setuptools
прямо назван error-prone, поскольку пакет ещё не установлен и его runtime-зависимости могут
отсутствовать. Пин `setuptools>=70` с запасом покрывает требуемую поддержку PEP 621
`dynamic` (появилась в setuptools 61.0.0), поэтому при соблюдении инварианта импорт пакета на
build stage не выполняется.

Нарушение инварианта 1 приводит к отказу сборки, а не к дефекту во время выполнения. Это
сознательно принятое свойство: ошибка обнаруживается максимально рано и громко.

## Import semantics

| Режим | Поведение |
|---|---|
| Установленный wheel | `__version__` читается из установленного модуля; `importlib.metadata.version("privacy-gateway")` возвращает то же значение |
| Editable install | То же; metadata сформирована на момент установки |
| Raw source tree без установки | `__version__` доступен и корректен; distribution metadata не требуется |

Поведение при отсутствии distribution metadata: импорт пакета и чтение `__version__` не
затрагиваются, так как обращения к `importlib.metadata` в import-пути нет. Отдельно
тестируется, что `privacy_gateway.__version__` доступен в процессе, где метаданные
`privacy-gateway` отсутствуют.

## Build semantics

- Wheel: `python -m build --wheel` даёт metadata `Version: 0.5.0`, извлечённую из AST
  `__init__.py`.
- Sdist: `python -m build --sdist` даёт архив, содержащий `src/privacy_gateway/__init__.py`;
  wheel, собранный из распакованного sdist, сообщает ту же версию.
- Editable: `pip install -e ".[dev]"` регистрирует metadata `0.5.0`.
- Сборка выполняется в build isolation: в рабочем `.venv` пакет `setuptools` не установлен,
  backend поставляется изолированным окружением по пину `>=70`. Фактическая версия backend
  фиксируется из build-лога, а не локальным `import setuptools`.

Ограничение editable-режима: metadata editable-установки не обновляется автоматически после
правки литерала. Расхождение до переустановки — ожидаемое состояние dev-окружения, а не
дефект; его обнаруживает сохранённый consistency-тест.

## Release process

Версия меняется ровно в одном месте — литерал `__version__` в
`src/privacy_gateway/__init__.py`. `pyproject.toml` при bump не редактируется.

Последовательность release после этого ADR:

1. изменить литерал `__version__`;
2. выполнить `python -m pip install -e ".[dev]"`, чтобы обновить metadata editable-установки;
3. выполнить локальный gate и build gate;
4. обновить CHANGELOG;
5. создать tag и Release по действующей процедуре.

Шаг 2 обязателен: без него consistency-тест сравнивает новый литерал с устаревшей metadata и
падает.

## Отвергнутые варианты

### A. `pyproject.toml` как источник, `__version__` через `importlib.metadata`

Механизм: `__version__ = importlib.metadata.version("privacy-gateway")`.

Отвергнут. `importlib.metadata.version()` возвращает версию установленного дистрибутива,
найденного в текущем окружении, а при его отсутствии поднимает `PackageNotFoundError`. Это
делает версию свойством окружения, а не импортированного кода. Sandbox-проверки этапа 0
выявили два сценария, где значение оказывается неверным без единой ошибки:

- оставшийся от предыдущей сборки каталог `src/*.egg-info` делает импорт из raw source
  «успешным» и возвращает версию из устаревших метаданных;
- при установленном в окружении дистрибутиве другой версии и текущем checkout впереди в
  `PYTHONPATH` пакет исполняет код одной версии, а сообщает версию другой.

Загрязнение рабочего дерева артефактами сборки в этом репозитории уже происходило и
разбиралось в follow-up #64. Под вариантом A тот же класс загрязнения превращается из
заметного расхождения счётчиков в тихо неверное значение версии.

Дополнительно A ломает импорт из исходников без установки, а запрет тихого fallback означает,
что это пришлось бы закрепить как контракт «пакет не поддерживает импорт без установленного
дистрибутива». Такого контракта у проекта нет, и вводить его ради устранения второй строки
несоразмерно. Также A добавляет чтение метаданных в import-путь библиотеки.

### C. Оставить два источника с consistency-тестом

Отвергнут. Вариант не создаёт единственного источника: две правки на release сохраняются,
а рассогласование обнаруживается только после установки. C рассматривался как резерв на
случай, если B не проходит build matrix; эксперименты этапа 0 такой несовместимости не
показали.

### VCS-based versioning (setuptools-scm и аналоги)

Не рассматривался в рамках #81, зафиксирован как отдельное возможное решение.

## Compatibility impact

- Публичный API не меняется: `privacy_gateway.__version__` остаётся строкой в `__all__`.
- Наблюдаемая версия остаётся `0.5.0` во всех режимах.
- CLI-контракты не меняются; флага `--version` не существует.
- Форматы артефактов и их версии не меняются; версия пакета в них не сериализуется.
- Runtime-зависимости не добавляются.
- Меняется семантика `pyproject.toml`: поле версии становится динамическим. Потребители,
  парсящие `project.version` из `pyproject.toml` напрямую, вместо строки увидят её отсутствие
  и запись в `dynamic`. Внутри репозитория таких потребителей этап 0 не обнаружил.

## Migration с 0.5.0 без version bump

Миграция состоит только в перемещении источника истины. Значение `0.5.0` не изменяется ни в
одном представлении: литерал в коде уже содержит `0.5.0`, и после удаления статического поля
метаданные wheel, sdist и editable-установки продолжают сообщать `0.5.0`. Опубликованный
Release v0.5.0 и существующие tags не затрагиваются.

## Rollback

Откат выполняется обратной правкой двух файлов и не требует изменения версии:

1. вернуть в `[project]` статическое `version = "0.5.0"`;
2. удалить `dynamic = ["version"]` и таблицу `[tool.setuptools.dynamic]` в части `version`;
3. оставить литерал `__version__` без изменений;
4. переустановить пакет и выполнить build gate.

После откатa репозиторий возвращается в состояние варианта C с двумя источниками и
сохранённым consistency-тестом. Артефакты, собранные до откатa, остаются валидными, так как
наблюдаемая версия не менялась.

## Test obligations

1. `privacy_gateway.__version__` — строка, непустая, присутствует в `__all__`.
2. `tests/test_cli.py::test_version_matches_distribution_metadata` сохраняется без ослабления
   и продолжает сравнивать `__version__` с `importlib.metadata.version("privacy-gateway")`.
3. Инвариант литерала проверяется статически: `__init__.py` разбирается через `ast`, значение
   `__version__` извлекается `ast.literal_eval`; тест падает, если присваивание перестало быть
   строковым литералом.
4. `__version__` доступен в процессе без distribution metadata пакета; отсутствие metadata не
   маскируется fallback-значением.
5. Build gate: editable install, wheel, sdist и wheel, собранный из sdist, сообщают `0.5.0`;
   wheel устанавливается в чистый venv вне репозитория.
6. Подтверждение на Python 3.11 и 3.12 через существующую CI matrix, а не ручным прогоном.
7. Временные build/dist/venv пути размещаются вне репозитория либо удаляются до gate, чтобы не
   влиять на mypy source count.
