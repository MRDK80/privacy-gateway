# ADR-303 addendum: owner-provisioned original final counter

Status: accepted design by owner on 2026-10-14; installation, provisioning and activation are not approved by this design decision.

## Source problem

Frozen build_entry imports entry policy before start's NOT_STARTED check. Missing launch-control cannot prove freshness: after control and preparation loss, existing source inputs can equal pristine inputs. Runtime must never initialize zero from missing files, start/resume flags, Session FINAL, or a candidate-provided callback/installed boolean.

## Selected boundary

Config8 requires original counter provisioning as a separate explicitly owner-approved setup action before activation. Autonomous runtime has no initialization writer effect. Frozen bootstrap source-validates mandatory original initialization artifacts, preparation profile and the existing role-state before candidate entry import for any path capable of model/new external effects. Missing/partial/mismatched original sources block. Existing bounded status, pause/stop and read-only pending reconciliation must remain available without creating/resetting counters or allowing model/new writes; their fixed authority guards remain required.

No additional config field or launch/control schema upgrade is needed. Fixed managed seed/final-initialization/{command-source.json,approval.json,approval-pin.json,install-receipt.json} is outside worktrees/model write mounts. Existing config8 preparation digest and verified launch digest bind all documents. Bootstrap uses only stdlib and existing private-source validators before candidate imports.

Closed initialization approval1 keys: schema_version("1.0"), repository, epic, owner_identity, mandate_digest, launch_digest, preparation_digest, counter_zero_digest, owner_command_digest, approved_at, approved_digest. Hash approved_digest excludes itself. The referenced zero is exactly existing sealed role_state1 with original identity, calls_consumed=0 and pending_reservation_digest=null; max final calls stays1, repairs0 and inherited mandate/session bounds remain unchanged.

Closed pin1 keys: schema_version("1.0"), repository, epic, owner_identity, mandate_digest, launch_digest, initialization_digest, installation_receipt_digest, record_digest. Closed receipt1 keys: schema_version("1.0"), kind("OWNER_FINAL_COUNTER_INITIALIZATION"), repository, epic, owner_identity, mandate_digest, launch_digest, initialization_digest, preparation_digest, counter_zero_digest, approved_at, owner_command_digest, record_digest. Ordinary digest conventions remain those of ADR303.

Provisioning is an original human setup ceremony before activation, requiring fresh exact owner approval for the actual invocation independently of seed documents. #303 implements neither a runtime initializer nor a reusable setup writer/CLI. The owner reviews the complete proposed zero, command/source descriptor and original launch/profile/mandate before separately authorizing their create-only placement under original seed ownership and serialization. Design approval does not authorize this ceremony. An old approval, timestamp, start flag or absent files cannot authorize another ceremony. Existing initialization provenance, partial state, control, reservation/cache/native settings or conflicting sources block original provisioning; absence of all these files is necessary but is not proof of freshness. The owner must establish that this is the original unactivated launch through the separately approved setup context. If history is unknown, stop and require a new separate owner disposition; #303 defines no automatic reset, renewal or recovery provisioning under that launch.

The fixed command/source descriptor is a bounded canonical record, not an executable command, candidate callback or proof of human identity. Closed command_source1 keys: schema_version("1.0"), kind("OWNER_ORIGINAL_FINAL_COUNTER_PROVISIONING"), procedure("ADR303_ORIGINAL_COUNTER_PROVISIONING_V1"), repository, epic, owner_identity, policy_sha, mandate_digest, launch_digest, preparation_digest, counter_zero_digest, record_digest. policy_sha must equal the reread original launch's trusted policy SHA; all other source identities equal the same reread original launch/profile/mandate/zero. The procedure denotes only this documented manual ceremony and does not select a runtime executable, path or implementation. owner_command_digest is the content hash of the complete sealed command_source1 at fixed command-source.json; both approval and receipt must bind it. The owner authorizes that exact descriptor together with the initialization approval. Runtime rereads descriptor, approval, receipt and pin from fixed paths; these internal links prove source consistency within the owner-installed boundary, not that a human freshly approved them. Independent explicit owner approval is an operational prerequisite, not inferred from those files. No external approval service or cryptographic approval implementation is introduced.

Digest order is acyclic: sealed original zero -> sealed command/source descriptor -> sealed initialization approval -> sealed receipt -> sealed pin. Each self digest excludes only itself; references cover complete sealed records. References use accepted ADR303 tagged source/untagged content digest conventions. Receipt initialization_digest and pin initialization_digest refer to the sealed approval; pin installation_receipt_digest refers to the sealed receipt. Receipt and approval cannot depend on pin.

Current zero must match its original referenced zero. Conservatively, any existing final-preparation/role-settings or final-preparation/sources path blocks zero, including an empty directory, inert ownership-only directory, unsafe path or retained receipt/cache. Any ordinal1 reservation also blocks zero. Bootstrap checks these fixed paths with no-follow metadata before candidate import and before a factory can create either namespace; it does not enumerate or infer receipt names. A partial first startup that creates such a namespace while still zero is BLOCKED on restart and requires separate owner disposition; availability is not restored by deleting it. Consumed1 validation uses its original bounded native chain. Current consumed1 is validated under original launch/profile and native source chain; it is not compared to zero's content hash. Source loss always blocks restoration, even if old initialization approval remains. Nonregular/link/duplicate/oversize/private-owner failure blocks. Complete records use the existing preparation max_artifact_bytes cap and inherited private-source limits. Bootstrap reads only the four named initialization files, fixed final-preparation/role-state.json, original launch/config/mandate/profile sources and existing fixed native/cache sources. Any reservation lookup is only the existing path derived from original launch plus ordinal1. Validate fixed directories without following links. This design adds no recursive scan or namespace enumeration; unexpected files cannot confer authority. Existing validators retain their bounded complete-source reads, and oversize evidence blocks without truncation.

As with existing owner/mandate installation, malicious same-OS-owner private-state writes remain outside the boundary; no stronger human identity, exactly-once, cross-file transaction or crash durability is claimed. The manual original setup obligation does not detect total history loss. Unknown history blocks the ceremony and runtime; a new explicit owner disposition is required outside this contract.

## Paths and tests

Cover build_entry/execute pre-import, entry start, entry.control initial/direct path, resume/direct child and partial setup. Every effect-capable path requires mandatory fixed original sources; no runtime path creates zero. Safe status/control/read-only reconciliation are classified by frozen bootstrap before candidate imports and preserve existing narrow authority guards without counter creation or new effects. Pin source is read-only in autonomous operation allowlist. Legacy config1–7 remain unchanged.

Synthetic source tests: approved original setup followed by initial start; no setup/old/partial pin; role-state loss and all preparation/control/cursor loss; zero replay retaining native receipts/cache or only an empty/inert role-settings/sources namespace; old setup documents never trigger runtime provisioning after consumption or missing sources; changed launch/profile/owner/mandate; imports cannot run before guard; pause/stop/read-only UNKNOWN reconciliation without new effects; original expiry/revoke/stop and single-call bounds. Config8 factory integration remains after reviewed302 baseline. Original final owner merge pin and real final demo remain separate.
