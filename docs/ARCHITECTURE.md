# Архитектура Privacy Gateway

Документ описывает фактическое состояние кода после этапов Э1–Э7 и мини-PR
`feat/route-v11-integrity`.

## Конвейер обработки

### Подготовка текста

```text
[входной текст: файл .txt / stdin]
        │
        ▼  input_parser.read_input()
           Читает файл или stdin с указанной кодировкой.
           Возвращает InputText{text, source, encoding, path}.
        │
        ▼  routing.load_routing_config(path)  [Э6]
           Загружает YAML-конфиг маршрутизации через yaml.safe_load.
           Возвращает RoutingConfig{output_dir, overwrite,
           tokenize_types, block_unconditionally}.
           Только безопасные умолчания при отсутствии файла.
        │
        ▼  keystore.get_key()
           Получает Fernet-ключ из системного keyring.
        │
        ▼  pipeline.prepare_pipeline(...)  [Э6]
           Сквозной конвейер:
           │
           ▼  detector.detect_entities(text, config)
              Применяет regex-паттерны и словарные записи из entities.yaml.
              Возвращает list[DetectedEntity] — без исходных значений,
              только fingerprint (SHA-256[:12]).
           │
           ▼  Фильтрация по RoutingConfig:
              block_unconditionally → немедленный BLOCKED.
              tokenize_types → только разрешённые типы передаются дальше.
           │
           ▼  tokenizer.tokenize(text, entities)
              Заменяет каждый span [start, end) на токен [TYPE_N].
              Возвращает (tokenized_text, list[TokenRecord]).
           │
           ▼  keystore.get_key()  ──►  crypto.encrypt(value, key)
              manifest.build_manifest(records, original_values, key)
              Шифрует каждое исходное значение Fernet-ключом.
              Возвращает list[ManifestEntry]{token, entity_type,
              fingerprint, encrypted_value (bytes)}.
           │
           ▼  manifest.save_manifest(entries, path)  [ШАГ 1]
              Записывает JSON-файл. encrypted_value — в hex.
              Права доступа: rw------- (только владелец).
              Исходные значения и ключ в файл не попадают.
           │
           ▼  hashlib.sha256(manifest_path.read_bytes())  [ШАГ 2]
              Читает байты уже записанного файла (после rename).
              SHA-256 включается в route_data как manifest_sha256.
           │
           ▼  validator.validate(tokenized_text)
              Два независимых прохода (без импорта detector.py):
              1. Негативный — email, IPv4/IPv6, телефоны,
                 secret_keyword, PEM, высокая энтропия (порог 3.0).
              2. Позитивный — формат [TYPE_N], вложенные/незакрытые
                 скобки, неизвестный тип токена.
              Возвращает ValidationResult{status, findings}.
           │
           ▼  При OK — атомарная запись артефактов [ШАГИ 3–4]:
              prompt.txt    — токенизированный текст (без исходных значений)
              route.json    — метаданные запуска, счётчики, manifest_sha256
              manifest.json — зашифрованная карта token→value
        │
        ▼  PipelineResult{ status: OK | BLOCKED | PENDING,
                           prompt_path, route_path, manifest_path }
```

### Восстановление текста

Ответ внешней LLM считается недоверенным входом. Команда `pgw restore`
проверяет связанные артефакты и классифицирует все кандидаты на токены до
записи результата.

```text
[ответ LLM: файл / stdin]
        │
        ▼  cli.restore()
           Читает ответ LLM и обязательный --route.
        │
        ▼  restore.restore_text(...)  [Э7]
           │
           ▼  1. Прочитать и разобрать route.json.
              Поддерживаются format_version "1.0" и "1.1".
              Неизвестная версия → ConfigurationError.
           │
           ▼  2. Выбрать manifest_path.
              --manifest имеет приоритет над route.json.
              Относительный путь из route.json разрешается относительно
              каталога самого route.json, а не рабочего каталога.
              Абсолютный путь используется как есть.
           │
           ▼  3. routing.verify_manifest_integrity(...)
              Вызывается для фактически выбранного manifest_path.
              Проверка выполняется до keyring, загрузки манифеста,
              расшифровки и обработки его содержимого.
           │
           ▼  4. keystore.get_key()
              Получает Fernet-ключ из системного keyring.
              Ошибка keyring или отсутствие ключа → код 4.
           │
           ▼  5. manifest.load_manifest(...)
              Загружает и расшифровывает записи манифеста.
              Чужой ключ или повреждённый шифртекст преобразуется
              в читаемую ошибку без traceback.
           │
           ▼  6. Классифицировать кандидаты на токены:
              известные, неизвестные, искажённые,
              пропавшие и дублированные.
           │
           ▼  7. В строгом режиме проверить отсутствие
              неизвестных и искажённых токенов.
              При отказе результат не записывается.
           │
           ▼  8. Подставить значения всех известных токенов.
              Дублированный токен заменяется во всех вхождениях.
           │
           ▼  9. Сформировать RestoreResult.
              Отчёт содержит только токены, счётчики и предупреждения,
              но не восстановленные значения.
           │
           ▼  10. Вывести результат в stdout либо атомарно записать
               его в файл через временный файл и os.replace().
        │
        ▼  восстановленный текст
```

Проверка целостности является обязательной границей между недоверенными
метаданными и использованием ключа. `verify_manifest_integrity` нельзя
переносить после `get_key`, `load_manifest` или расшифровки.

## Модель данных

### EntityType

`PERSON`, `ROLE`, `ORG`, `DEPARTMENT`, `EMAIL`, `PHONE`, `HOST`, `ENDPOINT`,
`RESOURCE`, `SYSTEM`, `PROJECT`, `AMOUNT`, `METRIC`, `DOCUMENT`, `DATE`,
`DURATION`, `ENVIRONMENT`.

### DetectionConfidence

`HIGH` — regex с высокой точностью (email, URL, IP, PEM).  
`MEDIUM` — regex с возможными ложными срабатываниями (телефоны, суммы) или
словарные совпадения.

### ProcessingStatus

| Значение | Семантика | Автоотправка |
|----------|-----------|-------------|
| `OK` | Текст токенизирован, остатков нет, все токены корректны | ✅ разрешена |
| `BLOCKED` | Остаточные PII/секреты или некорректные токены | ❌ запрещена |
| `PENDING` | Токен с неизвестным типом — нужно решение человека | ❌ запрещена |

**`PENDING` — не мягкий OK.** До явного одобрения оператора текст считается
небезопасным.

### RoutingConfig  [Э6]

Конфигурация маршрутизации обработки:

| Поле | Тип | Умолчание | Описание |
|------|-----|-----------|----------|
| `output_dir` | str | `./pgw_out` | Каталог для артефактов |
| `overwrite` | bool | `false` | Перезаписывать ли существующие файлы |
| `tokenize_types` | list[str] | все EntityType | Типы для токенизации |
| `block_unconditionally` | list[str] | `[]` | Типы, блокирующие обработку |

### PipelineResult  [Э6]

Результат конвейера `prepare_pipeline`:

| Поле | Тип | Условие |
|------|-----|---------|
| `status` | ProcessingStatus | всегда |
| `message` | str | всегда (без исходных значений) |
| `prompt_path` | Path \| None | только при OK |
| `route_path` | Path \| None | только при OK |
| `manifest_path` | Path \| None | только при OK |
| `findings_summary` | list[dict] | тип+позиция, без значений |

### RestoreResult  [Э7]

Результат `restore_text`:

| Поле | Тип | Семантика |
|------|-----|-----------|
| `restored_text` | str \| None | Восстановленный текст; `None` при строгом отказе |
| `tokens_expected` | set[str] | Токены из манифеста |
| `tokens_found` | set[str] | Известные токены, найденные в ответе |
| `tokens_missing` | set[str] | Токены манифеста, отсутствующие в ответе |
| `tokens_unknown` | set[str] | Корректные по формату токены вне манифеста |
| `tokens_malformed` | list[str] | Искажённые кандидаты |
| `tokens_duplicated` | set[str] | Известные токены с несколькими вхождениями |
| `warnings` | list[str] | Предупреждения без plaintext |
| `strict` | bool | Признак строгого режима |

`RestoreResult` используется для отчёта и контроля результата. Токены и
счётчики допустимы в отчёте; расшифрованные значения — нет.

### InputText

Хранит текст, источник (`file` / `stdin`), кодировку и опциональный путь.
`repr` не раскрывает содержимое текста.

### DetectedEntity

Хранит тип, диапазон `[start, end)`, уверенность, источник
(`regex` / `dictionary`) и fingerprint. Исходное значение **не хранится**.

### TokenRecord

Связывает токен (`[EMAIL_1]`) с fingerprint. Исходное значение не хранится.

### ManifestEntry

Содержит токен, тип сущности, fingerprint и `encrypted_value` (bytes).
В файле — hex.

## Форматы артефактов  [Э6 + мини-PR]

### prompt.txt

Токенизированный текст. Не содержит исходных значений.

### route.json — версия 1.1  [мини-PR]

Метаданные конвейера. Не содержит исходных значений, ключа, соли,
расшифрованных фрагментов.

```json
{
  "format_version": "1.1",
  "status": "OK",
  "timestamp": "<ISO-8601 UTC>",
  "source_ref": "<имя файла или stdin>",
  "manifest_path": "<путь к manifest.json>",
  "manifest_sha256": "<64 hex-символа lowercase>",
  "token_count": 3,
  "token_counts_by_type": {"EMAIL": 1, "HOST": 2},
  "entity_count_detected": 3,
  "entity_count_tokenized": 3
}
```

**`format_version`** читается командой `restore` для контроля совместимости.

**`manifest_sha256`** — SHA-256 всех байт файла `manifest.json` на его
финальном пути. Вычисляется **после** атомарной записи манифеста
(после `os.replace`/`rename`). Позволяет обнаружить рассинхронизацию пары
артефактов и повреждение файла манифеста целиком.

**Обратная совместимость:** файл `route.json` версии `1.0` без поля
`manifest_sha256` принимается командой `restore`;
`verify_manifest_integrity` пропускает проверку для версии `1.0`.

Файл версии `1.1` обязан содержать корректное поле `manifest_sha256`.
Неизвестные версии отклоняются без попытки загрузить или расшифровать
манифест.

**Функция проверки:**

```python
from privacy_gateway.routing import verify_manifest_integrity

verify_manifest_integrity(route_data: dict, manifest_path: Path) -> None
```

- Версия `1.1`, поле есть, сумма совпадает: функция завершается без ошибки.
- Версия `1.1`, несовпадение, отсутствие поля или файла:
  `ConfigurationError`.
- Версия `1.0`: проверка пропускается без ошибки.
- Неизвестная версия: `ConfigurationError`.

SHA-256 обеспечивает контроль целостности и связывание пары файлов, но не
аутентичность. Субъект, способный заменить оба файла, может пересчитать
контрольную сумму. Аутентичность каждой зашифрованной записи отдельно
обеспечивает Fernet.

### manifest.json

Зашифрованная карта token→value. Права доступа: rw------- (только владелец).
Подробнее — в разделе о криптографической схеме.

## Разрешение manifest_path  [Э7]

Путь к манифесту выбирается по следующим правилам:

1. Если передан `--manifest`, используется явно указанный путь.
2. Иначе используется поле `manifest_path` из `route.json`.
3. Абсолютный путь из `route.json` используется без преобразования.
4. Относительный путь из `route.json` разрешается относительно каталога
   самого `route.json`, а не текущего рабочего каталога.
5. `verify_manifest_integrity` получает фактически выбранный путь.

Это позволяет переносить каталог с артефактами целиком и запускать
`pgw restore` из произвольного рабочего каталога.

## Классификация токенов  [Э7]

Ответ LLM не считается доверенным. Каждый кандидат на токен должен попасть
в одну из явно определённых категорий.

| Категория | Пример | Поведение |
|-----------|--------|-----------|
| Известный | `[EMAIL_1]` есть в манифесте | Значение подставляется |
| Неизвестный | `[EMAIL_99]` отсутствует в манифесте | Строгий отказ; в `--lenient` остаётся без изменений |
| Искажённый | `[EMAIL_]`, `[EMAIL 1]`, `[[EMAIL_1]]`, `[email_1]` | Строгий отказ; в `--lenient` остаётся без изменений |
| Пропавший | Токен есть в манифесте, но отсутствует в ответе | Не ошибка; обязательно включается в отчёт |
| Дублированный | `[EMAIL_1]` встречается несколько раз | Подстановка во все вхождения; аномалия включается в отчёт |

Токены регистрозависимы: `[EMAIL_1]` и `[email_1]` не эквивалентны.
Автоматическая нормализация регистра запрещена, поскольку она маскировала
бы изменение ответа LLM.

Пропавший токен не подставляется в произвольное место. Отсутствие токена
может быть законным результатом суммаризации или переформулировки текста.

## Режимы восстановления  [Э7]

Строгий режим включён по умолчанию. Неизвестный или искажённый токен
приводит к отказу с ненулевым кодом. Результирующий файл при таком отказе
не создаётся.

Мягкий режим включается только явным флагом `--lenient`. В нём неизвестные
и искажённые кандидаты остаются в тексте без изменений и включаются в
предупреждения.

Пропавшие и дублированные известные токены не вызывают отказ сами по себе,
но обязательно отражаются в отчёте.

## Коды возврата restore  [Э7]

Существующая таблица кодов не изменяется:

| Результат restore | Код |
|-------------------|----:|
| Успешное восстановление | 0 |
| Непредвиденная ошибка | 1 |
| PENDING | 2 |
| Ошибка входа, конфигурации, целостности либо строгий отказ по токенам | 3 |
| Ошибка keystore или отсутствие ключа | 4 |

`ConfigurationError` от `verify_manifest_integrity`, ошибка входных данных
и строгий отказ из-за неизвестного или искажённого токена отображаются в
код 3.

`KeystoreError`, включая отсутствие ключа или недоступный keyring, приводит
к коду 4. Код 3 остаётся перегруженным; предложение по разделению его
семантики отложено до Э8.

## Криптографическая схема

**Алгоритм:** Fernet = AES-128-CBC + HMAC-SHA256
(аутентифицированное симметричное шифрование).

**Что шифруется:** исходные значения сущностей, каждое отдельно.

**Что на диске:**

```text
manifest.json  — token → encrypted_value (hex), fingerprint, entity_type
```

**Что НЕ на диске:** исходные значения в открытом виде, ключ шифрования.

**Где хранится ключ:** системный keyring.  
Service: `privacy-gateway`, Username: `fernet-key`.  
Байты ключа кодируются через `latin-1` для совместимости с keyring API.

**Валидация backend:** по полному имени класса (`module.qualname`) против
allowlist:

- `keyring.backends.SecretService.Keyring`
- `keyring.backends.macOS.Keyring`
- `keyring.backends.Windows.WinVaultKeyring`

При небезопасном или недоступном backend — `KeystoreError` до любой
операции.

**Порча шифртекста** детектируется: `Fernet.decrypt` поднимает
`InvalidToken`, который транслируется в `DecryptionError`.

## Атомарность записи артефактов  [Э6–Э7]

### Подготовка

Артефакты создаются **только при статусе OK**. При BLOCKED или PENDING ни
одного файла не создаётся.

Запись `prompt.txt` и `route.json` выполняется через временный файл в той же
директории с последующим `rename` — атомарной операцией в пределах одной
файловой системы.

Порядок записи при OK:

1. `manifest.json` — атомарно через `save_manifest` с последующим `chmod`.
2. SHA-256 читается из финального пути `manifest_path`, после `rename`.
3. `prompt.txt` — атомарно.
4. `route.json` с `manifest_sha256` — атомарно.

### Восстановление

Результат `restore` сначала полностью формируется и проверяется в памяти.
Только после успешной проверки он записывается во временный файл в
каталоге назначения и заменяет конечный файл через `os.replace`.

Если конечный файл уже существует и не передан `--overwrite`, команда
завершается с отказом. При ошибке строгого режима, целостности, keyring,
загрузки или расшифровки конечный и временный файлы не должны оставаться
на диске.

## Отчёт восстановления  [Э7]

Отчёт сообщает:

- сколько токенов ожидалось;
- сколько известных токенов найдено и восстановлено;
- какие токены отсутствовали;
- какие токены оказались неизвестными;
- какие кандидаты были искажены;
- какие известные токены дублировались;
- применялся ли строгий режим;
- предупреждения мягкого режима.

Отчёт не содержит исходные или восстановленные значения, шифротекст,
Fernet-ключ либо полное содержимое манифеста. Это ограничение действует
как для штатного отчёта, так и для сообщений об ошибках.

## Почему валидатор независим от детектора

Детектор Э3 настроен на отзыв с допустимым числом ложных срабатываний: его
задача — найти как можно больше, не засоряя вывод. Валидатор Э5 —
независимый рубеж с противоположной задачей: **доказать отсутствие**
остатков.

Асимметрия цены ошибки:

- Ошибка детектора (пропуск) → валидатор поймёт → статус BLOCKED, утечки нет.
- Ошибка валидатора (пропуск) → утечка ПДн во внешнюю LLM.

Поэтому валидатор дублирует паттерны сознательно, не импортирует
`detector.py` и не использует его конфигурацию. Независимость рубежей —
это защита от единой точки отказа.

## Границы доверия

| Вход или компонент | Уровень доверия | Контроль |
|--------------------|-----------------|----------|
| Исходный текст | Недоверенный | Детекция и независимая валидация |
| YAML-конфиг | Недоверенный | `yaml.safe_load`, строгая схема, fail closed |
| Ответ LLM | Недоверенный | Классификация токенов, строгий режим |
| `route.json` | Недоверенный | Проверка версии и обязательных полей |
| `manifest.json` | Недоверенный до проверки | SHA-256 пары и Fernet-аутентификация записей |
| Keyring backend | Недоверенный до проверки | Allowlist полного имени класса |
| Отчёт и ошибки | Потенциально журналируемые данные | Запрет на plaintext |

## Кроссплатформенные решения

| Аспект | Решение |
|--------|----------|
| Пути в коде | Только `pathlib.Path` |
| Относительный manifest_path | Разрешается относительно каталога route.json |
| Детектор RESOURCE | Распознаёт UNC, `C:\...` и `/opt/...` независимо от ОС |
| Кодировки | Явная передача: `utf-8`, `utf-8-sig`, `cp1251` |
| Unicode при restore | Текст читается и записывается в UTF-8 |
| Переводы строк | Сохраняются при побайтовом сквозном цикле |
| Атомарная запись | Временный файл в каталоге назначения + `os.replace` |
| Права manifest.json | `chmod` с игнорированием ошибок на Windows |
| CI | Матрица `ubuntu-latest` + `windows-latest` |
