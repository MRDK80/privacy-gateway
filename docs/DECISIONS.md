# Реестр архитектурных решений (ADR)

Документ фиксирует принятые решения для Privacy Gateway после этапов Э1–Э8.
Формат: контекст → решение → обоснование → последствия → статус.

---

## ADR-01: Fernet как алгоритм шифрования

**Контекст.** Нужно шифровать исходные значения сущностей для хранения в манифесте. Требования: аутентифицированное шифрование, стандартная библиотека, простота.

**Решение.** Fernet (AES-128-CBC + HMAC-SHA256) из пакета `cryptography`.

**Обоснование.** Аутентифицированное шифрование — порча шифртекста детектируется немедленно. Fernet реализован в стандартной библиотеке `cryptography`, которая уже является зависимостью. Нет необходимости в собственной криптографии.

**Последствия.** Ключ — 32 байта в base64url. Манифесты зашифрованы конкретным ключом; при его смене старые манифесты нечитаемы без явной ротации (см. ADR-06).

**Статус:** действует.

## ADR-02: Ключ в системном keyring

**Контекст.** Fernet-ключ нужно где-то хранить между запусками. Файл на диске — ненадёжно. Переменная окружения — утечка в логи и историю.

**Решение.** Хранить ключ в системном keyring через библиотеку `keyring`. Service: `privacy-gateway`, Username: `fernet-key`. Байты ключа кодируются через `latin-1` для совместимости с keyring API (строки).

**Обоснование.** Системные хранилища (SecretService / macOS Keychain / Windows Credential Vault) предоставляют шифрование «из коробки» с привязкой к учётной записи пользователя.

**Последствия.** На headless Linux необходим `dbus-run-session + gnome-keyring-daemon`. В CI нужен mock или `PGW_KEYRING_BACKEND`. Backend валидируется по allowlist до любой операции (fail closed).

**Статус:** действует.

## ADR-03: Валидация backend keyring по allowlist

**Контекст.** Библиотека `keyring` может автоматически выбрать небезопасный backend (plaintext, in-memory) на headless системах.

**Решение.** Валидировать backend по полному имени класса (`module.qualname`) против allowlist: `SecretService.Keyring`, `macOS.Keyring`, `WinVaultKeyring`. Override через `PGW_KEYRING_BACKEND` также проходит валидацию. При несоответствии — `KeystoreError` до записи или чтения ключа.

**Обоснование.** Fail closed: лучше упасть с ошибкой, чем молча записать ключ в plaintext-хранилище.

**Последствия.** На неподдерживаемых системах или в CI без настройки операции с ключом не работают. Это намеренное поведение.

**Статус:** действует.

## ADR-04: Стабильность токенов — вариант A (per-document)

**Контекст.** Нужно определить область стабильности токенов: одинаковое значение (`user@example.com`) в одном документе должно получать один и тот же токен (`[EMAIL_1]`), но поведение между запусками не оговорено.

**Решение.** Вариант A: счётчик и словарь `seen` живут внутри одного документа (одного вызова `tokenize()`). Состояние между запусками не сохраняется.

**Обоснование.** Простейшая реализация. Манифест уже хранит все соответствия — сквозная стабильность не нужна для восстановления в рамках одного документа.

**Последствия.** `[EMAIL_1]` в двух разных запусках может соответствовать разным адресам. Важно при ручной обработке.

**Отложено:** вариант B (глобальный реестр токенов между запусками) — рассмотреть в Э7.

**Статус:** действует.

## ADR-05: Манифест хранит только token → encrypted_value

**Контекст.** Нужно определить, что именно хранится в файле манифеста.

**Решение.** Манифест содержит только: `token`, `entity_type`, `fingerprint`, `encrypted_value` (hex). Исходные значения в открытом виде отсутствуют. Ключ не записывается.

**Обоснование.** Файл манифеста может попасть в систему контроля версий или в резервную копию. Без ключа он бесполезен для злоумышленника.

**Последствия.** Для восстановления исходных значений необходим и манифест, и ключ из keyring.

**Статус:** действует.

## ADR-06: MultiFernet обеспечивает чтение манифестов после ротации ключа  [Э8]

**Контекст.** В ADR-06 (исходная редакция) было зафиксировано, что `MultiFernet` не реализован и ротация ключа делает старые манифесты нечитаемыми. Это было принято как намеренное ограничение с пометкой «отложено на Э8».

**Решение.** В Э8 реализован `MultiFernet`: `encrypt_multi(plaintext, keys)` шифрует первым ключом списка; `decrypt_multi(ciphertext, keys)` пробует все ключи по очереди до первого успешного расшифрования. `keystore.get_all_keys()` возвращает список `[active_key, retired_key]` (новый первым). `restore_text` использует `get_all_keys()` и `decrypt_multi`, что обеспечивает чтение манифестов, созданных до последней ротации, без ручных действий.

**Обоснование.** Ротация ключа без обратной совместимости создаёт операционный риск: все манифесты, созданные до ротации, становятся недоступными. MultiFernet — стандартный паттерн для Fernet, устраняющий этот риск при минимальном усложнении.

**Ограничения.** Поддерживается только одна итерация ротации (один retired-ключ). Манифесты, созданные до предпоследней ротации, нечитаемы. При удалении ключа (`pgw key delete`) обратная совместимость утрачивается необратимо.

**Последствия.** `restore_text` читает манифесты, созданные как до, так и после последней ротации. `prepare_pipeline` шифрует только активным ключом. Удаление ключа документированно необратимо.

**Статус:** действует (реализовано в Э8, заменяет исходную редакцию ADR-06).

## ADR-07: Валидатор независим от детектора

**Контекст.** Валидатор (Э5) проверяет выход токенизатора. Можно было бы переиспользовать паттерны из `detector.py`.

**Решение.** Импорт `detector.py` в `validator.py` запрещён. Паттерны дублируются.

**Обоснование.** Асимметрия цены ошибки: ошибка детектора (пропуск) — валидатор поймает. Ошибка валидатора (пропуск) — утечка ПДн. Два независимых рубежа устраняют единую точку отказа. Детектор настроен на отзыв; валидатор — на точность с порогом энтропии 3.0 (vs ~3.5 у детектора).

**Последствия.** При изменении паттернов в `detector.py` нужно отдельно обновлять `validator.py`. Это намеренная стоимость независимости.

**Статус:** действует.

## ADR-08: Fail closed как сквозной принцип

**Контекст.** Во многих точках системы возможна неоднозначность: небезопасный keyring backend, неизвестный тип токена, повреждённый шифртекст.

**Решение.** При любой неоднозначности — безопасный исход: `KeystoreError` (keystore), `BLOCKED` / `PENDING` (validator), `DecryptionError` (crypto).

**Обоснование.** Цена ложной тревоги (ручная проверка) значительно ниже цены ложного OK (утечка ПДн).

**Последствия.** Пользователь будет видеть ошибки при нестандартных конфигурациях. Это намеренное поведение, а не баг.

**Статус:** действует.

## ADR-09: Стратегия токенизации вынесена в Protocol

**Контекст.** Поведение присвоения токенов (нумерация, область стабильности) может потребоваться заменить без изменения публичного API.

**Решение.** `TokenAssignmentStrategy` — Protocol с методом `assign(entity, value) -> str`. `PerDocumentStrategy` — дефолтная реализация (вариант A). Стратегия передаётся в `tokenize()` как параметр.

**Обоснование.** Позволяет подменить стратегию в тестах и в будущих этапах (вариант B) без изменения вызывающего кода.

**Последствия.** Стратегии можно тестировать изолированно. Вариант B (глобальный реестр) реализуем как отдельный класс.

**Статус:** действует.

## ADR-10: YAML-конфиг загружается только через yaml.safe_load  [Э6]

**Контекст.** Конфиг маршрутизации читается из файла, который может контролировать злоумышленник.

**Решение.** Единственный способ загрузки YAML в `routing.py` — `yaml.safe_load`. Использование `yaml.load` или `yaml.full_load` запрещено. Неизвестные ключи на верхнем уровне и в секции `rules` — явная `ConfigurationError`.

**Обоснование.** `yaml.load` с произвольными тегами (`!!python/object/apply`) позволяет выполнить произвольный код. `safe_load` отклоняет такие теги, что предотвращает deserialization-атаку.

**Последствия.** Конфиг с нестандартными YAML-тегами не будет загружен. Это намеренное ограничение.

**Статус:** действует.

## ADR-11: Конфиг не может отключить проверку секретов (fail closed)  [Э6]

**Контекст.** Конфиг маршрутизации позволяет задавать `block_unconditionally` и `tokenize`. Теоретически можно попытаться включить тип SECRET в `tokenize`, чтобы обойти блокировку.

**Решение.** Пересечение `tokenize_types` и `block_unconditionally` — явная `ConfigurationError`. Конфиг не может ослабить проверку безопасности.

**Обоснование.** Fail closed: конфигурационный файл — не привилегированный канал управления безопасностью. Безопасность не должна зависеть от корректности пользовательского конфига.

**Последствия.** Пользователи не могут случайно или намеренно настроить токенизацию типов, которые должны блокировать обработку.

**Статус:** действует.

## ADR-12: Артефакты создаются атомарно через временный файл  [Э6]

**Контекст.** При записи `prompt.txt` и `route.json` возможен сбой в середине записи, что оставит частично записанный файл.

**Решение.** Запись через `tempfile.mkstemp` в той же директории с последующим `Path.replace` (атомарный `rename` в пределах одной файловой системы).

**Обоснование.** `rename` атомарен на POSIX. На Windows атомарность гарантирована начиная с Python 3.3+ (`Path.replace`). Частично записанный файл недоступен читателю до завершения записи.

**Последствия.** Артефакты либо созданы полностью, либо не созданы вовсе. Нет промежуточного состояния.

**Статус:** действует.

## ADR-13: route.json содержит format_version  [Э6]

**Контекст.** Этап Э7 будет читать `route.json` для восстановления. Схема файла может меняться.

**Решение.** `route.json` содержит поле `format_version: "1.0"`. Значение константы `ROUTE_FORMAT_VERSION` определено в `pipeline.py`.

**Обоснование.** Явное версионирование формата позволяет Э7 и последующим этапам проверять совместимость и отклонять устаревшие файлы с понятным сообщением об ошибке.

**Последствия.** При изменении схемы `route.json` необходимо обновить версию и миграционную логику в Э7.

**Статус:** действует.

## ADR-14: Связывание route.json и manifest.json контрольной суммой

**Контекст.** Команда `pgw prepare` создаёт связанную пару артефактов: `route.json` содержит метаданные запуска и путь к `manifest.json`, а манифест содержит зашифрованные соответствия токенов исходным значениям. Формат `route.json` версии `1.0` не позволяет до начала восстановления определить, относится ли манифест к этому запуску, а также обнаружить повреждение файла манифеста целиком.

**Решение.** Поднять `format_version` файла `route.json` до `"1.1"` и добавить обязательное поле `manifest_sha256` — SHA-256 всех байтов финального `manifest.json` в виде 64 шестнадцатеричных символов нижнего регистра. Сначала `manifest.json` атомарно записывается на финальный путь, затем читаются байты этого финального файла и вычисляется контрольная сумма, после чего `route.json` с полученным значением атомарно записывается на диск.

Для проверки пары предоставляется публичная функция:

```python
def verify_manifest_integrity(
    route_data: dict,
    manifest_path: Path,
) -> None:
```

Для `format_version == "1.1"` функция требует поле `manifest_sha256`, вычисляет SHA-256 фактических байтов указанного манифеста и безопасно сравнивает значения. Несовпадение, отсутствие обязательного поля, отсутствие файла и неизвестная версия вызывают явную `ConfigurationError` с сообщением, не раскрывающим содержимое манифеста. Для версии `"1.0"` проверка пропускается ради обратной совместимости.

**Обоснование.** Контрольная сумма обеспечивает обнаружение рассинхронизации пары артефактов и повреждения файла манифеста до обработки его содержимого. Вычисление суммы после завершения атомарной записи гарантирует, что в `route.json` зафиксирован хеш именно финальных байтов файла, доступных последующему читателю.

**Ограничения.** SHA-256 без цифровой подписи или MAC не обеспечивает аутентичность и не является защитой от целенаправленной подмены. Субъект, способный заменить оба файла, может пересчитать контрольную сумму. Fernet отдельно аутентифицирует каждую зашифрованную запись манифеста; поле `manifest_sha256` не заменяет эту проверку и связывает только пару файлов целиком.

**Последствия.** Новые запуски `prepare` создают `route.json` версии `"1.1"` с обязательным полем `manifest_sha256`. Читатели должны принимать версию `"1.0"` без проверки контрольной суммы, проверять пару для версии `"1.1"` и явно отклонять неизвестные версии. Формат `manifest.json`, таблица кодов возврата и криптографическая схема не изменяются.

**Статус:** действует.

## ADR-15: Разрешение относительного manifest_path  [Э7]

**Контекст.** Команда `pgw restore` получает путь к `route.json` и должна найти соответствующий `manifest.json`. Поле `manifest_path` в `route.json` может быть относительным. Вопрос: относительно чего его разрешать — рабочего каталога или расположения самого `route.json`?

**Решение.** Относительный `manifest_path` разрешается относительно каталога, содержащего `route.json`, а не текущего рабочего каталога процесса. Абсолютный путь используется как есть. Явный флаг `--manifest` переопределяет путь из `route.json` и принимается в любом виде (абсолютный или относительный к рабочему каталогу). Проверка целостности (`verify_manifest_integrity`) проводится для фактически выбранного пути.

**Обоснование.** `route.json` и `manifest.json` создаются вместе командой `prepare` и физически находятся рядом. Разрешение относительно каталога `route.json` позволяет запускать `pgw restore` из произвольного рабочего каталога без необходимости менять `cd`. Это соответствует поведению большинства инструментов, работающих с конфигурационными файлами.

**Последствия.** Пара артефактов переносима: достаточно переместить директорию целиком. Флаг `--manifest` даёт явное управление для нестандартных сценариев.

**Статус:** действует.

## ADR-16: Строгий режим по умолчанию и семантика --lenient  [Э7]

**Контекст.** При восстановлении текста могут встретиться неизвестные или искажённые токены — токены, которых нет в манифесте либо которые не соответствуют формату `[TYPE_N]`. Нужно определить, как система должна реагировать по умолчанию.

**Решение.** Строгий режим включён по умолчанию (`strict=True`). В строгом режиме любой неизвестный или искажённый токен вызывает `RestoreError` с ненулевым кодом возврата (3). При строгом отказе результирующий файл не создаётся — `restored_text` возвращается как `None`. Мягкий режим включается только явным флагом `--lenient`. В мягком режиме неизвестные и искажённые кандидаты остаются в тексте без изменений и отражаются в предупреждениях. Отчёт в stderr никогда не содержит восстановленных (plaintext) значений — только счётчики и токены.

**Обоснование.** Fail closed (см. ADR-08): неизвестный токен в ответе LLM скорее свидетельствует о галлюцинации модели или манипуляции, чем о штатной ситуации. Безопаснее завершиться с ошибкой, чем молча передать частично восстановленный текст. Мягкий режим доступен, но требует явного opt-in.

**Последствия.** Пользователи, ожидающие частичного восстановления, должны явно передавать `--lenient`. CI-пайплайны по умолчанию получают строгое поведение без дополнительной настройки.

**Статус:** действует.

## ADR-17: Поведение при пропавших токенах  [Э7]

**Контекст.** Токен может присутствовать в манифесте (был создан на этапе `prepare`), но отсутствовать в ответе LLM. Это может означать, что модель законно исключила фрагмент текста или переформулировала его без использования токена.

**Решение.** Токен, присутствующий в манифесте, но не найденный ни в одном месте ответа LLM, считается пропавшим. Пропавший токен не является ошибкой сам по себе и не вызывает отказ ни в строгом, ни в мягком режиме. Пропавший токен обязательно включается в отчёт/предупреждение (`tokens_missing`). Пропавший токен не подставляется в произвольное место текста.

**Обоснование.** LLM может законно опустить часть текста. Принудительный сбой при пропавшем токене создал бы ложные срабатывания для нормальных сценариев суммаризации и переформулировки.

**Последствия.** Оператор может обнаружить пропавшие токены через отчёт и принять решение вручную. Автоматической компенсации нет.

**Статус:** действует.

## ADR-18: Поведение при дублированных токенах  [Э7]

**Контекст.** Один и тот же токен (например, `[EMAIL_1]`) может встретиться в ответе LLM несколько раз. Нужно определить, является ли это ошибкой и как обрабатывать подстановку.

**Решение.** Если известный токен встречается в ответе LLM более одного раза, значение подставляется во все его вхождения без исключения. Дублирование считается аномалией и фиксируется в отчёте (`tokens_duplicated`). Само по себе дублирование не вызывает отказ ни в строгом, ни в мягком режиме.

**Обоснование.** LLM может повторить токен при цитировании или перечислении. Отказ восстановления из-за дубля был бы чрезмерно строгим. Фиксация в отчёте позволяет оператору отследить нестандартное поведение модели.

**Последствия.** Результирующий текст будет содержать plaintext-значение во всех позициях, где встречался токен. Оператор видит счётчик дублей в отчёте.

**Статус:** действует.

## ADR-19: Регистрозависимость токенов  [Э7]

**Контекст.** Токены имеют формат `[TYPE_N]`, где TYPE записан заглавными буквами. LLM теоретически может вернуть токен в изменённом регистре, например `[email_1]` вместо `[EMAIL_1]`. Нужно определить, считать ли такие варианты эквивалентными.

**Решение.** Токены регистрозависимы. `[EMAIL_1]` и `[email_1]` не являются эквивалентными токенами. Вариант с изменённым или смешанным регистром классифицируется как искажённый кандидат (`tokens_malformed`), а не как известный или неизвестный токен. Автоматическая нормализация регистра запрещена.

**Обоснование.** Автоматическая нормализация регистра маскировала бы изменение токена в ответе LLM, что противоречит принципу fail closed (ADR-08). Изменение регистра токена — признак галлюцинации или манипуляции, который должен быть обнаружен.

**Последствия.** В строгом режиме токен с неверным регистром вызывает отказ с кодом 3. В мягком режиме он остаётся в тексте как есть и фиксируется в предупреждениях.

**Статус:** действует.

## ADR-20: Коды возврата команды restore  [Э7]

**Контекст.** Команда `pgw restore` может завершаться по нескольким причинам: успешное восстановление, различные категории ошибок. Нужно зафиксировать таблицу кодов возврата и её семантику.

**Решение.** Таблица кодов возврата (не изменяется в Э7):

| Результат restore | Код |
|---|---:|
| Успешное восстановление | 0 |
| Непредвиденная ошибка | 1 |
| PENDING | 2 |
| Ошибка входа, конфигурации, целостности либо строгий отказ по токенам | 3 |
| Ошибка keystore или отсутствие ключа | 4 |

Уточнения к коду 3: `ConfigurationError` от `verify_manifest_integrity` отображается в код 3; неизвестный или искажённый токен в строгом режиме (`RestoreError`) также приводит к коду 3. Уточнения к коду 4: отсутствие ключа в keyring (`KeyNotFoundError`) и любая ошибка keystore (`KeystoreError`) приводят к коду 4.

**Обоснование.** Значение кода 3 перегружено: оно объединяет ошибки конфигурации/целостности и строгий отказ по токенам. В Э7 таблица не меняется ради минимальности изменений публичного контракта. Разведение кода 3 на два отдельных кода готовится для Э8.

**Последствия.** Скрипты, анализирующие код возврата `pgw restore`, должны учитывать, что код 3 охватывает несколько семантически разных классов ошибок. Уточнение будет выполнено в Э8 без изменения существующих кодов.

**Отложено:** разведение кода 3 — выполнено в Э8, см. ADR-21.

**Статус:** заменён ADR-21.

## ADR-21: Разведение кодов 3 и 5 — строгий токенный отказ  [Э8]

**Контекст.** В ADR-20 код 3 объединяет два семантически разных класса ошибок: ошибки конфигурации/целостности (невалидный `route.json`, нарушение `manifest_sha256`) и строгий отказ по токенам (неизвестный или искажённый токен в ответе LLM). Это затрудняет автоматический анализ кода возврата в CI-пайплайнах.

**Решение.** Ввести отдельный код возврата **5** для строгого токенного отказа. Обновлённая таблица кодов возврата команды `pgw restore`:

| Результат restore | Код |
|---|---:|
| Успешное восстановление | 0 |
| Непредвиденная ошибка | 1 |
| PENDING | 2 |
| Ошибка конфигурации или целостности (`ConfigurationError`, `RestoreError`) | 3 |
| Ошибка keystore или отсутствие ключа | 4 |
| Строгий отказ по токенам (`RestoreStrictError`) | 5 |

В реализации: `RestoreStrictError` — отдельный класс исключения, наследник `Exception` (не `RestoreError`). CLI отлавливает `RestoreStrictError` явно и завершается с кодом 5 до общего обработчика `RestoreError` (код 3).

**Обоснование.** Коды 3 и 5 имеют разную семантику для оператора: код 3 означает повреждение или некорректную конфигурацию (требует вмешательства администратора); код 5 означает, что LLM вернул недопустимые токены (требует ревью ответа модели или переключения в `--lenient`). Разведение позволяет CI-скриптам реагировать по-разному без разбора текста ошибки.

**Последствия.** Скрипты, ранее проверявшие только код 3 для строгого отказа, требуют обновления: добавить проверку кода 5. Коды 0–4 остаются совместимы с Э7.

**Статус:** действует.

## ADR-22: Интерфейс команды pgw key  [Э8]

**Контекст.** В Э8 добавляется управление жизненным циклом ключа через CLI. Нужно зафиксировать публичный контракт подкоманд.

**Решение.** Добавить группу подкоманд `pgw key` с тремя операциями:

| Подкоманда | Действие |
|---|---|
| `pgw key create` | Создать новый активный ключ (ошибка, если ключ уже существует) |
| `pgw key rotate` | Создать новый ключ, сохранить текущий как retired |
| `pgw key delete` | Удалить активный ключ и retired-ключ (необратимо) |

`pgw key create` завершается с кодом 1, если активный ключ уже существует — повторное создание без явного `rotate` запрещено. `pgw key rotate` атомарен в смысле keystore: сначала записывается retired, затем active; сбой до завершения второй записи оставляет active без изменений. `pgw key delete` выводит предупреждение о необратимости и требует подтверждения (`--yes`) в интерактивном режиме.

**Обоснование.** Явный интерфейс предотвращает случайную перезапись ключа без ротации (потеря всех манифестов). Атомарность в смысле keystore минимизирует риск оставить систему в состоянии, где нет ни active, ни retired ключа.

**Последствия.** Пользователи не могут молча перезаписать ключ — только через явный `rotate`. Удаление задокументировано как необратимая операция.

**Статус:** действует.

## ADR-23: MultiFernet обеспечивает обратную совместимость при ротации  [Э8]

**Контекст.** После реализации `MultiFernet` (ADR-06 обновлённая редакция) нужно явно зафиксировать границы гарантии обратной совместимости и поведение `decrypt_multi`.

**Решение.** `decrypt_multi(ciphertext, keys)` принимает список ключей и пробует их по очереди до первого успешного расшифрования. `encrypt_multi(plaintext, keys)` шифрует только первым ключом списка (`keys[0]`). `get_all_keys()` возвращает список `[active_key, *retired_keys]` — новый ключ первым. Гарантия совместимости: манифест, созданный с любым ключом из текущего `get_all_keys()`, успешно расшифровывается. После удаления ключа (`pgw key delete`) гарантия утрачивается для всех манифестов, зашифрованных этим ключом.

**Обоснование.** Порядок ключей в `get_all_keys()` (новый первым) гарантирует, что новые манифесты расшифровываются с первой попытки. Старые манифесты расшифровываются со второй попытки (retired-ключ). Производительность O(1) для типичного случая (один active, один retired).

**Ограничения.** Поддерживается один уровень ротации. Цепочки из трёх и более ключей не гарантируются текущей реализацией.

**Последствия.** `restore_text` использует `get_all_keys()` + `decrypt_multi` и прозрачно работает с манифестами до и после последней ротации. Явное удаление ключа — единственный способ необратимо сделать манифест нечитаемым.

**Статус:** действует.

## ADR-24: Отчёт restore не содержит plaintext-значений  [Э8]

**Контекст.** `RestoreResult` и сообщения в stderr команды `pgw restore` могут содержать информацию о токенах. Нужно явно зафиксировать границу между допустимыми и недопустимыми данными в отчёте.

**Решение.** `RestoreResult` и все сообщения в stderr содержат только: счётчики (`tokens_found_count`, `tokens_missing_count` и т. д.), имена токенов (`[EMAIL_1]`, `[IP_2]`), предупреждения с именами токенов. Исходные (plaintext) значения, частично восстановленный текст и фрагменты зашифрованных записей в отчёт не включаются. Это требование распространяется на `findings_summary` в `PipelineResult` (только тип, правило, позиция — без значения) и на сообщения `BLOCKED`/`PENDING` в `prepare`.

**Обоснование.** Отчёт может записываться в логи CI, передаваться через API мониторинга или сохраняться в артефактах сборки. Попадание ПДн в лог-строку создаёт вторичный вектор утечки, труднее контролируемый, чем манифест.

**Последствия.** Отчёт безопасен для записи в неограниченные логи. Отладка конкретных значений требует расшифровки манифеста вручную.

**Статус:** действует.

## ADR-25: Тестовые данные — только синтетика  [Э8]

**Контекст.** Тесты работают с примерами email-адресов, IP-адресов и телефонных номеров. Нужно определить требования к допустимым тестовым данным.

**Решение.** Все тестовые данные в `tests/` используют исключительно синтетические значения из зарезервированных диапазонов и доменов:

- Email: `user@example.com`, `admin@example.org`, `*@example.net` и аналогичные (RFC 2606)
- IP: диапазон `192.0.2.0/24` (TEST-NET-1, RFC 5737), `198.51.100.0/24`, `203.0.113.0/24`
- IPv6: `2001:db8::/32` (RFC 3849)
- Телефоны: `+7 900 000-00-00`, `+1 (555) 000-0000` и аналогичные заведомо несуществующие номера
- Имена: вымышленные (не принадлежащие реальным публичным лицам)

Использование реальных ПДн (реальные email, IP публичных лиц, реальные телефоны) в тестах запрещено.

**Обоснование.** Тестовые данные попадают в историю git, CI-логи и артефакты сборки. Даже в тестовом контексте реальные ПДн создают нежелательные риски: соответствие требованиям GDPR/152-ФЗ, репутационные риски, нежелательная индексация.

**Последствия.** Код-ревью должен отклонять тесты с реальными ПДн. Синтетические диапазоны достаточны для покрытия всех функциональных сценариев.

**Статус:** действует.

## ADR-26: Публичный фасад как единственная точка интеграции  [#14]

**Контекст.** Внешним приложениям требовался способ использовать Privacy Gateway без CLI. Прямой импорт `pipeline`, `restore`, `manifest` и `keystore` привязывал бы потребителя к внутренней структуре проекта.

**Решение.** Добавлен модуль `facade.py` с классом `PrivacyGateway` и публичными моделями, а также `exceptions.py` с публичной иерархией ошибок. Единственный поддерживаемый путь импорта — пакет верхнего уровня; состав контракта задаёт `__all__`. Фасад не дублирует детекцию, токенизацию, шифрование и manifest: он вызывает существующий конвейер.

**Обоснование.** Один фасад вместо нескольких конкурирующих API. Внутренние модули остаются свободными для изменений, пока публичный контракт стабилен.

**Последствия.** Пакет помечен `py.typed`. Изменения внутренних сигнатур не ломают потребителя, но требуют поддерживать трансляцию в публичный контракт. CLI остаётся независимым потребителем того же конвейера (см. #18).

**Статус:** действует.

## ADR-27: Контекст восстановления непрозрачен, рабочим каталогом владеет фасад  [#14]

**Контекст.** Конвейер файловый: `prepare` пишет `prompt.txt`, `manifest.json` и `route.json`, а `restore` читает `route.json`. Передавать потребителю пути и содержимое manifest нельзя.

**Решение.** `prepare` возвращает `RestoreContext` без публичных полей с данными. Каждая подготовка получает собственный рабочий подкаталог: временный с правами владельца либо подкаталог внутри `workspace_dir`. Контекст сериализуем через `to_token`/`from_token`, переживает перезапуск процесса, пригоден для повторного использования и удаляется явным `discard`. Автоматического удаления нет.

**Обоснование.** Непрозрачность закрывает утечку структуры manifest. Отдельный подкаталог на операцию даёт изоляцию параллельных вызовов и позволяет считать экземпляр потокобезопасным. Явное удаление необходимо: ответ внешнего обработчика может прийти отложенно.

**Последствия.** Ответственность за очистку лежит на приложении-потребителе; при `keep_artifacts=True` — полностью. Наружу отдаются только счётчики токенов, не их имена.

**Статус:** действует.

## ADR-28: Трансляция внутренних ошибок в публичные  [#14]

**Контекст.** Внутренний слой использует перегруженный `ConfigurationError` (конфигурация, целостность, расшифровка, запись файла), отдельный `RestoreError` в `restore.py` и `RestoreStrictError` в `models.py`.

**Решение.** Фасад транслирует внутренние исключения в публичные через exception chaining. Нарушение целостности, неизвестная версия формата и неудачная расшифровка отображаются в `IntegrityError`; отсутствие контекста — в `RestoreError`; строгий токенный отказ — в `StrictTokenError`, наследник `RestoreError`; ошибки хранилища ключей — в `KeyStoreError`; fail-closed при подготовке — в `DetectionError` с нейтральным атрибутом `status`.

**Обоснование.** Потребителю нужно различать проблему с артефактами и проблему с ответом внешнего обработчика: реакция разная. Публичные классы не наследуют внутренние, поэтому внутреннюю иерархию можно менять, не ломая контракт.

**Последствия.** Сообщения публичных ошибок не содержат plaintext, ключи, шифртекст, имена токенов и содержимое manifest. Коды завершения CLI к публичным исключениям отношения не имеют.

**Статус:** действует.

## ADR-29: Ошибка использования CLI отображается в код 3  [#26]

**Контекст:** ADR-20 и ADR-21 определяют коды результатов обработки, где код 2
означает PENDING — требуется ручное одобрение. argparse по умолчанию завершает
процесс кодом 2 при синтаксической ошибке вызова. Внешний вызывающий код не мог
отличить корректно обработанный PENDING от неверно вызванной команды.

**Решение:** синтаксическая ошибка разбора командной строки отображается в код
3 — тот же код, что и ошибки входных данных, конфигурации и целостности. Код 2
резервируется исключительно за PENDING. Перехват выполняется только на границе
первичного разбора argv (`_parse_args` в `cli.py`): argparse к этому моменту уже
напечатал usage/error, поэтому stderr не изменяется побайтово. `--help` и help
подкоманд сохраняют код 0.

**Отвергнутые варианты:**

- только задокументировать совпадение кодов — двусмысленность сохраняется, а
  именно она и была причиной задачи;
- перенести PENDING на другой код — ломает контракт успешной обработки для
  потребителей 0.3.0 сильнее, чем правка usage error;
- подкласс `ArgumentParser` с переопределением `error()` — шире по охвату,
  требует доказательства распространения на все subparsers и рискует изменить
  формат stderr.

**Последствия:** изменение наблюдаемого поведения CLI, зафиксировано в
CHANGELOG. Команды, флаги и коды 0/1/4/5 не изменились. Расхождение `pgw key`
без подкоманды (код 0 через поздний help) остаётся предметом #30, ошибка записи
restore (код 1) — предметом #28.

**Статус:** принят. Уточняет ADR-20 и ADR-21, не заменяет их.

## ADR-30. Отсутствие обязательной команды — ошибка использования

Статус: принят. Уточняет ADR-29, не заменяет его. Задача #30.

### Контекст

`pgw` без команды печатал help вручную и выходил кодом 1. `pgw key` без подкоманды
вызывал `parser.parse_args(["key", "--help"])`, help-action завершал процесс кодом 0,
поэтому следующий `sys.exit(1)` был недостижим. Неизвестная команда после ADR-29 уже
давала код 3. Один класс ошибки вызова сообщался тремя разными кодами, включая код успеха,
что опасно для shell и CI, проверяющих только код возврата.

### Решение

Верхнеуровневые subparsers и subparsers группы `key` объявляются с `required=True`.
Отсутствие и неизвестное значение команды обрабатывает единый механизм argparse,
`_parse_args()` транслирует usage error в код 3 (ADR-29). Ручная печать help с кодами
0 и 1 удалена вместе с недостижимым `sys.exit(1)`. Явный `--help` на верхнем и
key-уровне остаётся кодом 0. Код 2 остаётся закреплён исключительно за PENDING.

| Вызов | До | После |
|---|---:|---:|
| `pgw` | 1 | 3 |
| `pgw unknown` | 3 | 3 |
| `pgw key` | 0 | 3 |
| `pgw key unknown` | 3 | 3 |
| `pgw --help` | 0 | 0 |
| `pgw key --help` | 0 | 0 |
| PENDING | 2 | 2 |

### Отвергнутые варианты

- Ручная печать help подпарсера `key` с кодом 1: после ADR-29 код 1 означает непредвиденную
  ошибку, тогда как неполная команда — ожидаемая ошибка использования; кроме того,
  сохраняется отдельный путь, отличный от неизвестной подкоманды.
- Закрепить текущий код 0: успех при неполной команде противоречит ADR-29 и опасен для CI.
- Исправить только `key`, оставив верхнеуровневый `pgw` с кодом 1: сохраняет расхождение,
  которое пришлось бы обосновывать отдельным решением.

### Следствия

Внешний вызывающий код различает: 0 — успех, 2 — требуется ручное одобрение,
3 — ошибка использования или содержательный отказ, 4 — keystore, 5 — строгий отказ restore.
Вызовы, полагавшиеся на код 0 у `pgw key`, получают 3; это и есть цель изменения.

## ADR-31: Код завершения при ошибке записи результата restore  [#28]

**Контекст.** Фаза записи результата `restore` обрабатывала два исключения
по-разному: `FileExistsError` давал код 3, а `ConfigurationError` из
`write_restored` — код 1. Тот же `ConfigurationError` на остальных участках
CLI даёт 3. Анализ реализации показал, что `ConfigurationError` здесь
оборачивает исключительно `OSError` от `mkstemp`, записи во временный файл
и `os.replace`.

**Решение.** `ConfigurationError`, поднятый фазой записи результата
`restore`, отображается в код завершения 3. `FileExistsError` остаётся 3 с
prefix `Ошибка`. Prefix `Ошибка записи` сохраняется побайтово. Неизвестное
исключение фазы записи остаётся кодом 1. Отдельный внутренний тип
исключения не вводится. Отвергнут вариант «признать код 1 корректным».

**Обоснование.** Невозможность записать указанный внешним вызывающим кодом
output path — ожидаемый операционный отказ окружения, а не непредвиденная
внутренняя ошибка. По матрице после ADR-29/30 это относится к коду 3.

**Последствия.** Наблюдаемое поведение CLI меняется: `pgw restore --out` при
отказе файловой системы завершается кодом 3 вместо 1. Текст stderr не
меняется. ADR-31 уточняет ADR-21 и mapping из #18 и не заменяет ADR-29/30.

**Статус:** действует.

## ADR-32: Источник token_count для публичного результата prepare  [#32]

**Контекст.** `prepare_pipeline` вычисляет число токенов как
`len(token_records)` и записывает его в `route.json`. Публичный фасад после
успешного конвейера повторно читал этот файл и разбирал JSON ради того же
числа, потому что `PipelineResult` его не отдавал. Цена: лишнее чтение
защищённого артефакта на каждый `prepare`, зависимость фасада от имени поля
внутреннего формата route, версией которого владеет `pipeline.py`, и путь, в
котором уже успешная подготовка завершалась `ConfigurationError` из-за отказа
повторного чтения.

**Решение.** Метаданные, уже известные механизму, возвращаются внутренним
результатом. В `PipelineResult` добавлено поле `token_count: int = 0`,
заполняемое той же величиной, что попадает в `route.json`; одна локальная
переменная используется и для route, и для результата. Фактический счётчик
получает только результат со статусом OK, остальные возвраты сохраняют 0.
Фасад берёт `result.token_count`, `_read_token_count` удалён, fallback-разбор
route не вводится. Чтение `prompt.txt` остаётся. Отвергнуты повторное чтение
артефакта и отдельный прикладной слой (#27, закрыт как not planned).

**Обоснование.** `token_count` — агрегированный счётчик без plaintext, ключей,
имён токенов и содержимого manifest, поэтому его передача внутренним
результатом не расширяет раскрытие по ADR-26 и ADR-27. Источник значения
единственный, что исключает расхождение route и результата.

**Последствия.** Публичный `PreparedPayload.token_count` не изменился по типу
и значениям, `route.json` и `ROUTE_FORMAT_VERSION` 1.1 сохранены побайтово по
составу полей, CLI не затронут. Поле внутреннее и не экспортируется через
`privacy_gateway.__all__`; значение по умолчанию сохраняет совместимость
тестовых конструкторов из #25. Тестов 279 → 284.

**Статус:** действует.

## ADR-33: Отказ подготовки каталога при записи результата restore — код 3

Дата: 2026-08-19
Статус: Принято
Контекст: #36, уточняет ADR-31, связано с ADR-12, ADR-21

### Контекст

`write_restored` выполняет запись результата `restore --out` атомарно: создание
родительского каталога, `tempfile.mkstemp`, запись, `os.replace`. После ADR-31
`OSError` от `mkstemp`, записи и `os.replace` преобразуется в
`ConfigurationError` и отображается кодом 3 с prefix `Ошибка записи`, а создание
родительского каталога находилось вне этой границы: его `OSError` проходил
наружу сырым, попадал в общий обработчик и печатался как
`Непредвиденная ошибка` с кодом 1.

Причина отказа одна и та же — невозможность записать результат по выбранному
пути, — а наблюдаемый код зависел от того, существует ли родительский каталог.

### Решение

Все `OSError` внутри операции `write_restored`, включая подготовку каталога,
считаются ожидаемыми отказами записи:

- механизм записи преобразует их в `ConfigurationError`;
- CLI отображает `ConfigurationError` из фазы записи кодом 3 с prefix
  `Ошибка записи` по ADR-31;
- неизвестные не-`OSError` по-прежнему проходят наружу и дают код 1 с prefix
  `Непредвиденная ошибка`;
- автоматическое создание отсутствующих родительских каталогов для `--out`
  сохраняется.

Граница расширена минимальным изменением control flow: строка
`out_path.parent.mkdir(parents=True, exist_ok=True)` перенесена внутрь
существующего внешнего `try`. Это безопасно, потому что cleanup временного файла
обращается к `tmp_name` только во внутреннем блоке после успешного `mkstemp`,
поэтому расширение `try` не создаёт `UnboundLocalError`.

### Отвергнутые варианты

- Признать код 1 корректным для отказа `mkdir`: сохраняет расхождение внутри
  одного класса причин и противоречит ADR-31.
- Запретить создание отсутствующих родительских каталогов и считать их
  отсутствие ошибкой ввода: это второй breaking change в одной задаче;
  пользователи уже могут рассчитывать на `--out nested/path/file`.
- Добавить правило на широкий `OSError` в `cli.py`: адаптер классифицировал бы
  как ожидаемый отказ записи любую файловую ошибку любого происхождения и
  потерял бы контекст, а библиотечные потребители `write_restored` перестали бы
  получать единый внутренний тип.

### Следствия

- Наблюдаемое изменение: отказ создания родительского каталога при
  `restore --out` даёт код 3 вместо 1, prefix stderr становится
  `Ошибка записи` вместо `Непредвиденная ошибка`.
- Восстановленный текст в stdout/stderr при отказе не попадает: сообщение
  содержит только путь и системную причину.
- Временные файлы после отказа не остаются: при отказе `mkdir` временный файл
  ещё не создавался.
- Алгоритм атомарной записи, `FileExistsError` и его текст, `overwrite`,
  `_RESTORE_WRITE_RULES`, `cli.py` и публичный фасад не изменены.

## ADR-34: доверенность контекста восстановления и подтверждение владения рабочим каталогом  [#43]

**Дата:** 2026-08-22. **Статус:** принято.
**Связано:** #42 (источник finding), #49 (remediation-roadmap), ADR-06, ADR-12,
ADR-23, ADR-26, ADR-27, ADR-28.

### Контекст

Аудит #42 на ревизии `6900b117` установил, что сериализованный
`RestoreContext` не аутентифицирован. `to_token()` возвращал
`base64url(json)` над полями `handle`, `route`, `workspace`, `owned`,
`correlation_id`, а `PrivacyGateway.discard()` проверял единственное поле
`_owned_workspace` и передавал `_workspace_dir` в
`shutil.rmtree(..., ignore_errors=True)`. Любой доступный процессу каталог
удалялся по контексту, который атакующий сконструировал сам, причём
`ignore_errors=True` скрывал следы.

### Граница доверия

Контекст создаёт `prepare` внутри доверенной области фасада. Сериализует,
хранит и возвращает его приложение-потребитель: по ADR-27 контекст намеренно
переживает перезапуск процесса, то есть токен живёт в недоверенном хранилище
(файл, очередь, база приложения).

Атакующий может читать и изменять токен, подставлять произвольный абсолютный
путь, `..`-траверсал и sibling-каталог с общим префиксом имени, создавать
каталоги и ссылки, подменять компонент пути между проверкой и удалением.
Защищаются пользовательские файлы вне рабочего каталога, ключевой материал,
содержимое manifest и восстановленный plaintext.

### Решение

Право на удаление даёт доказанное владение конкретным каталогом. Механизм —
сочетание секрета владения и проверки принадлежности.

1. **Секрет владения.** `prepare` генерирует `secrets.token_hex(32)` и пишет
   его в маркер `.pgw-owner` внутри рабочего каталога через `O_EXCL` с правами
   `0600`, в формате «версия формата / handle / секрет». Полезная нагрузка
   токена подписывается HMAC-SHA256 на ключе, выведенном из этого секрета с
   доменным разделением `privacy-gateway/restore-context/v2`.
2. **Принадлежность.** Перед удалением проверяются: совпадение доверенной базы
   из конфигурации фасада с базой в контексте, canonical containment в этой
   базе, существование пути, что путь — настоящий каталог без symlink и
   reparse point, наличие маркера с тем же `handle`, совпадение MAC и
   повторная сверка `(st_dev, st_ino)` непосредственно перед `rmtree`.

Порядок фиксирован и fail-closed: при любом отказе не удаляется ничего.
Containment вычисляется по компонентам пути после `os.path.realpath` через
`Path.relative_to`; строковый префикс (`startswith` и эквиваленты) не
используется. Доверенная база берётся из `GatewayConfig.workspace_dir`, а при
`None` — из канонического системного временного каталога; из токена она только
сверяется, но не принимается.

### Отклонённые альтернативы

| Альтернатива | Причина отклонения |
|---|---|
| Ключ MAC из keystore | Ставит освобождение ресурсов в зависимость от доступности ключа: после `pgw key delete`, при заблокированном keyring и в headless-окружении `discard` поднимал бы `KeyStoreError`, и защищённые артефакты остались бы на диске. Ослабление существующей гарантии cleanup. Проверено практикой: реализация этого варианта дала 4 падения на существующих тестах фасада. |
| Секрет в памяти экземпляра | Ломает ADR-27: контекст перестаёт переживать перезапуск процесса и передачу между процессами. |
| Только строковый префикс пути | Пробивается sibling-каталогом с общим префиксом имени и не учитывает ссылки. |
| Только проверка существования каталога | Существование пути ничего не говорит о владении. |
| Шифрование токена вместо MAC | Конфиденциальность служебных ссылок целью #43 не является; нужна целостность, а MAC дешевле и проще для проверки. |
| Отдельный долгоживущий секрет для MAC | Требует нового жизненного цикла секрета и его хранения; секрет уровня workspace такого цикла не требует. |

### Жизненный цикл секрета

Секрет создаётся вместе с рабочим каталогом и исчезает вместе с ним. Он не
попадает в токен, в `repr` моделей, в сообщения об ошибках и в keystore.
Ротация и удаление Fernet-ключа на проверку владения не влияют.

### Привязка к handle

Маркер хранит `handle` операции, и проверка требует его совпадения с `handle`
контекста. Это закрывает удаление другого собственного рабочего каталога
внутри той же доверенной базы: подделанный указатель на соседний workspace
даёт несовпадение `handle` и отказ.

### Ссылки и TOCTOU

Финальный компонент проверяется через `lstat` без следования ссылкам; junction
и symlink на Windows определяются по `FILE_ATTRIBUTE_REPARSE_POINT`. Symlink в
родительском компоненте выводит `realpath` за пределы базы, и containment
отказывает. Против подмены между проверкой и удалением снимается пара
`(st_dev, st_ino)` и сверяется непосредственно перед удалением. Контрактное
поведение Linux и Windows одинаково, различаются только низкоуровневые
проверки.

### Совместимость

`CONTEXT_FORMAT_VERSION` меняется с `1` на `2`. Токены, выданные версией
`v0.4.0`, не принимаются: `from_token` поднимает `RestoreError`. Приём
неподписанных токенов сохранил бы уязвимость целиком, а контекст по назначению
живёт в пределах одной операции prepare → внешний обработчик → restore. Это
ломающее изменение публичного контракта, отражено в CHANGELOG и
`docs/SECURITY.md`.

### Публичное поведение

| Ситуация | Результат |
|---|---|
| Изменённый, чужой, вышедший за базу контекст | `RestoreError` |
| Каталог без маркера, с чужим `handle` или подделанным маркером | `RestoreError` |
| Рабочий каталог подменён ссылкой | `RestoreError`, внешняя цель не удаляется |
| Подмена каталога между проверкой и удалением | `RestoreError` |
| Отсутствующая подпись, версия `1`, повреждённая сериализация | `RestoreError` при разборе токена |
| Рабочий каталог уже удалён | Вызов идемпотентен, ошибки нет |
| `keep_artifacts=True` | Артефакты сохраняются, ошибки нет |

Новых публичных классов ошибок не добавлено, состав `__all__` не расширен,
CLI и формат manifest не затронуты. Сообщения не содержат путей, секретов,
значений и имён токенов.

### Ограничения и остаточные риски

- Локальный пользователь с правом записи внутрь доверенной базы может подложить
  маркер. Рекомендация — выделенный `workspace_dir`, недоступный на запись
  другим процессам; при `workspace_dir=None` библиотека владеет собственным
  подкаталогом временного каталога.
- Сверка `(st_dev, st_ino)` сужает окно TOCTOU, но не устраняет его без
  `openat`-семантики по всем компонентам пути.
- Механизм не защищает от субъекта, уже имеющего права на удаление целевого
  каталога средствами ОС.

### Дополнение (2026-08-22): race-safe граница удаления  [#43]

PR #50 оставлял окно между последней сверкой `(st_dev, st_ino)` и path-based
`shutil.rmtree()`: обе операции разрешали атакуемое имя заново, поэтому
подмена финального или родительского компонента после последней проверки не
обнаруживалась. Формулировка «подмена между проверкой и удалением →
`RestoreError`» была сильнее фактической гарантии.

Решение: destructive operation работает над проверенной сущностью. Каталог
отцепляется от исходного имени переименованием в непредсказуемое карантинное
имя внутри того же родителя, идентичность объекта под карантинным именем
сверяется с идентичностью, снятой до отцепления, и только после этого
выполняется рекурсивное удаление. Атакуемое имя в удалении не участвует.
Секрет владения, на котором проверен MAC контекста, дополнительно сверяется с
секретом, прочитанным на самой границе удаления: аутентичность токена
привязана к сущности, а не к пути.

Механизмы различаются по платформам осознанно:

| Платформа | Механизм | Гарантия |
|---|---|---|
| Linux и подобные | Родитель и рабочий каталог открываются с `O_DIRECTORY` и `O_NOFOLLOW`, идентичность снимается `fstat`, маркер читается через `dir_fd`, отцепление — `renameat`, обход дерева — `rmtree(dir_fd=...)` при истинном `avoids_symlink_attacks` | Проверенный inode закреплён дескриптором: подмена любого компонента имени после проверки на удаление не влияет |
| Windows | Отцепление имени с повторной сверкой: `os.rename`, затем повторные проверки идентичности и маркера под карантинным именем | Окно радикально сужено, но не устранено на уровне ядра: `os.supports_dir_fd` пуст, эквивалента `openat` в поддерживаемом Python 3.11 нет, а `CreateFileW` с `FILE_FLAG_BACKUP_SEMANTICS` требует native-зависимости, которая не подтверждена |

Публичное поведение одинаково: при любом расхождении на границе удаления
поднимается `RestoreError` и не удаляется ничего. Отцепленный объект при
отказе не удаляется, а исходное имя восстанавливается best-effort и только
если оно свободно.

Рекурсивное удаление после отцепления остаётся best-effort
(`ignore_errors=True`): решение о безопасности принято на границе отцепления,
частичный отказ уборки доверия не меняет и сохраняет прежнее наблюдаемое
поведение `discard`.

`workspace_identity()` заменена на `path_identity()`, работающую и
относительно `dir_fd`. Формат маркера, `CONTEXT_FORMAT_VERSION`, состав
токена, `__all__`, CLI и формат manifest не изменены: совместимость v2
сохранена.

Тесты границы — `tests/test_discard_race_boundary.py`: подмена исходного имени
ссылкой непосредственно перед первым destructive syscall на обеих ветках
механизма, расхождение идентичности после отцепления, несовпадение секрета на
границе, сохранность уборки валидного owned workspace и гигиена сообщений. Тестов
309 → 316.

Остаточный риск, который дополнение не снимает: на Windows подмена объекта в
момент самого `rename` теоретически возможна, хотя повторная сверка
идентичности и маркера не даёт удалить чужой объект. Симметричная
kernel-атомарная гарантия там требует отдельного решения по native-слою.


### Дополнение (2026-08-22): привязка destructive operation к сущности  [#52]

Дополнение от 2026-08-22 (PR #51) отцепляло проверенный каталог в
непредсказуемое карантинное имя, но оставляло окно между последней проверкой
идентичности и началом рекурсивного удаления: `shutil.rmtree()` получал
карантинное **имя** и разрешал его заново. Ожидаемая идентичность в `rmtree`
не передаётся, поэтому его собственная symlink-защита согласована только со
своим же `lstat`, а не с проверкой вызывающего кода.

Дефект воспроизведён детерминированно на неизменённом `main` для обеих ветвей
механизма: непосредственно перед `rmtree` проверенный quarantine
переименовывается, а под прежним карантинным именем создаётся другой реальный
каталог с контрольным файлом и вложенным поддеревом. До исправления удаляется
подставленный каталог целиком, а проверенная сущность остаётся. Случайность
карантинного имени сужала окно, но границей безопасности не являлась.

Отдельно исправлена неполная post-rename проверка маркера в ветви без
`dir_fd`: проверялось наличие маркера с совпадающим `handle`, но найденный
секрет не сравнивался с аутентифицированным.

**Решение.** Рекурсивное удаление начинается от объекта, закреплённого
дескриптором или handle, и ни на одном шаге не принимает заново разрешённый
pathname как самостоятельное основание для удаления. Финальное снятие имени
выполняется только при совпадении идентичности с ранее проверенной.

| Платформа | Механизм | Гарантия |
|---|---|---|
| Linux и подобные (`SUPPORTS_DIR_FD`) | `O_DIRECTORY`/`O_NOFOLLOW`, `fstat`, маркер через `dir_fd`, `renameat`; обход дерева от удерживаемого дескриптора с `openat` и `samestat` на каждом шаге; финальный `rmdir` относительно родителя только при совпадении идентичности | Удаление привязано к проверенному inode на всём протяжении операции; подмена любого компонента имени после проверки на результат не влияет |
| Windows Server 2016 / 10 1607 (build 14393) и новее — базовый механизм | Handle каталога с `FILE_FLAG_BACKUP_SEMANTICS` и `FILE_FLAG_OPEN_REPARSE_POINT`; идентичность — `GetFileInformationByHandleEx(FileIdInfo)`; reparse point — `FileAttributeTagInfo`; перечисление — `FileIdBothDirectoryInfo`; дети открываются относительно handle через `NtCreateFile` с `ObjectAttributes.RootDirectory`; удаление — `SetFileInformationByHandle(FileDispositionInfo)` на handle объекта | Удаление привязано к закреплённой сущности; имя после отцепления в destructive-вызове не участвует. Имя исчезает при закрытии последнего handle, поэтому обход строго снизу вверх |
| Windows 10 1709 (build 16299) и новее — оптимизация | То же, но диспозиция ставится через `FileDispositionInfoEx` с `FILE_DISPOSITION_POSIX_SEMANTICS` | Имя уходит из namespace немедленно, остаточных delete-pending имён не возникает |
| Платформа, где инвариант закрепления не выполняется | Fail closed без рекурсивного удаления | Остаточный карантинный объект допустим; удаление неподтверждённой сущности недопустимо |

Минимальная поддерживаемая Windows — Server 2016, поэтому основным механизмом
считается `FileDispositionInfo`, а `FileDispositionInfoEx` применяется как
оптимизация при её доступности. Отказ Ex-варианта с `ERROR_NOT_SUPPORTED` (50)
на сборках ниже 16299 обрабатывается как ожидаемый переход на базовый
механизм, а не как ошибка.

Механизм не деградирует молча. Если в рантайме не выполняется любой из
инвариантов закрепления — не получена идентичность через handle или
дескриптор, недоступно относительное открытие ребёнка, идентичность после
отцепления не совпала, маркер на границе не сошёлся — операция завершается
`RestoreError` без рекурсивного удаления. Path-based рекурсивное удаление как
fallback не используется ни при каких условиях.

Инварианты, обязательные до первого destructive-вызова:

1. доверенная база из конфигурации фасада и canonical containment;
2. объект — настоящий каталог, без symlink, junction и reparse point;
3. идентичность снята с закреплённого объекта, а не с имени;
4. маркер владения содержит тот же `handle`;
5. секрет из маркера совпадает с секретом, на котором проверен MAC контекста,
   и сравнивается через `hmac.compare_digest`;
6. идентичность закреплённого объекта после отцепления не изменилась;
7. проверка маркера повторена после отцепления.

**Отклонённые альтернативы.**

- `shutil.rmtree(path, dir_fd=parent_fd)` как единственная защита: обход
  согласован только со своим `lstat`, ожидаемая идентичность извне не
  принимается.
- Расчёт на непредсказуемость карантинного имени: имя появляется в файловой
  системе и наблюдаемо; это сужение окна, а не граница безопасности.
- `FILE_FLAG_DELETE_ON_CLOSE` вместо диспозиции: не сообщает
  `STATUS_DIRECTORY_NOT_EMPTY`, частичные отказы становятся ненаблюдаемыми.
- Сторонняя native-зависимость для Windows: не одобрена; используется только
  stdlib `ctypes`, административные привилегии не требуются.

**Остаточные риски и границы утверждения.**

- Слой `NtCreateFile` с `ObjectAttributes.RootDirectory` описан в DDI, но не
  входит в стабильный Win32 API: `CreateFileW` относительного открытия не
  предоставляет. Совместимость держится на рантайм-проверках и тестах, а не на
  гарантии стабильности интерфейса.
- Состояние delete-pending не считается защитой от переиспользования имени: в
  разведке на build 14393 повторное открытие delete-pending каталога по имени
  прошло, хотя документированное поведение — `ERROR_ACCESS_DENIED`. Гарантия
  механизма от этого не зависит, поскольку имя после отцепления не
  используется.
- На базовом механизме Windows диспозиция необратима: сброс через
  `FILE_DISPOSITION_DO_NOT_DELETE` доступен только вместе с Ex-вариантом,
  поэтому диспозиция ставится последней операцией, после всех проверок.
- Полнота уборки остаётся best-effort: решение о безопасности принимается на
  границе закрепления, частичный отказ уборки доверия не меняет.
- Рабочая база, доступная на запись недоверенным процессам, остаётся
  архитектурным риском: рекомендуется выделенный `workspace_dir`.

**Совместимость.** `CONTEXT_FORMAT_VERSION` остаётся 2; состав токена, формат
маркера, `__all__`, CLI, коды завершения, `ROUTE_FORMAT_VERSION` и формат
manifest не затронуты. Новых публичных исключений и зависимостей нет.

#### Доказательная база и её асимметрия

Уровень доказательности различается по платформам, и это фиксируется явно.

| Утверждение | Как доказано | Уровень |
|---|---|---|
| Дефект существует на обеих ветвях `main` | Детерминированное воспроизведение quarantine-swap реальным каталогом; трассировка от post-rename проверки до первого `unlink` показала, что `rmtree` заново открывает карантинное имя после закрытия проверенного дескриптора | Прямое доказательство |
| Post-rename секрет не сравнивался | Воспроизведено двумя независимыми способами: подменой последовательности чтений маркера и перезаписью маркера на файловой системе после `rename` | Прямое доказательство |
| Linux: обход от закреплённого дескриптора выдерживает подмену | Прототип на том же swap-сценарии: подставленный каталог и его содержимое сохранены, проверенная сущность вычищена, валидная уборка не нарушена | Прямое доказательство |
| Windows, сборки ≥ 16299 | CONFIRM: заполнить из артефактов probe | Формальное доказательство в условиях модели угроз #52 |
| Windows, build 14393 (минимальная поддерживаемая) | Два повторяемых прогона probe: шесть prerequisites выполнены, `swap_defended: true`, `valid_cleanup_intact: true`, `mechanisms_used: ["legacy"]`, Ex отклонён с `ERROR_NOT_SUPPORTED` (50), отказ на непустом каталоге — `ERROR_DIR_NOT_EMPTY` (145). Условия отличались от требуемых: Python 3.13.2 и права администратора, поэтому вердикт probe — `inconclusive` | Фактическое подтверждение с оговоркой |

Оговорка по build 14393: проверяемые операции выполняются через `ctypes`
напрямую в `kernel32` и `ntdll`, поэтому от версии интерпретатора не зависят;
привилегии не влияют на доступ к объектам, созданным тем же пользователем в
собственном временном каталоге. Прогон в полном соответствии условиям на этой
сборке не выполнен: GitHub-hosted образа Windows Server 2016 не существует, а
self-hosted раннер на такой машине недоступен.

Формулировка «доказано в условиях модели угроз #52» применима только к строке
о сборках ≥ 16299. Для build 14393 используется формулировка «подтверждено
повторяемыми прогонами на минимальной поддерживаемой сборке; прогон в полном
соответствии условиям не выполнен». Остаточная неполнота компенсируется тестом
инварианта `test_pinning_unavailable_fails_closed`, который проверяет само
поведение кода, а не конкретную сборку.

Остаточное поведение после успешного удаления также различается по
платформам и не является дефектом. На Linux финальный `rmdir` называет
карантинное имя только для проверки идентичности; если оно подставлено
атакующим, проверенная сущность, уже переехавшая под другое имя, остаётся
пустым каталогом — устранение этого артефакта требует именования по пути,
чего механизм принципиально не делает. На Windows диспозиция ставится на сам
handle закреплённого объекта и не зависит от текущего имени, поэтому
сущность удаляется целиком независимо от подмены имени. Оба поведения
удовлетворяют инварианту #52: неподтверждённая сущность не удаляется,
подтверждённая — не остаётся доступной под прежним содержимым. Зафиксировано
тестами `test_quarantine_swap_real_directory_pinned` (Linux) и
`test_quarantine_swap_real_directory_handle` (Windows).

### Дополнение (2026-08-22): граница противника и остаточные гонки  [#54]

Это дополнение уточняет границу утверждений ADR-34 после PR #53 и не изменяет
историческое описание решения #52.

#### Граница противника

В модели угроз атакующий контролирует сериализованный `RestoreContext`: может
изменять поля токена, пути, флаг владения и correlation metadata, а также
подменять namespace entries в родительском каталоге workspace в пределах прав
ОС. Он не имеет права читать или изменять содержимое owned workspace с режимом
`0700`, не имеет доступа к памяти процесса и owner secret.

Вне модели находятся процесс с той же OS identity и прямым доступом внутрь
workspace или к `.pgw-owner`, субъект, который уже может удалить либо
переписать целевой объект средствами ОС, и компрометация памяти процесса или
owner secret. Owner secret хранится внутри workspace; защита от same-identity
субъекта, способного его прочитать, требует отдельной OS identity, sandbox или
другой системной границы.

Root quarantine race отличается от гонок внутри содержимого workspace. PR #53
закрепляет корень descriptor/handle и начинает рекурсивный обход от этого
объекта. Имена детей разрешаются относительно закреплённого родителя.
Child-entry mutation процессом с прямым write-доступом внутрь workspace
находится вне принятой модели угроз.

#### POSIX final-rmdir residual

После очистки дерева `_rmdir_verified()` сверяет identity объекта под
quarantine-именем, затем вызывает `rmdir(quarantine, dir_fd=parent_fd)` по
имени относительно закреплённого parent descriptor. Между identity-check и
`rmdir` остаётся namespace race.

Подмена непустым каталогом приводит к отказу `rmdir` без рекурсивного удаления.
Подмена пустым каталогом может удалить только пустую namespace entry. Поэтому
остаток классифицируется как ограниченный namespace/DoS-риск, а не как
возможность произвольного рекурсивного удаления данных и не как абсолютная
race-free гарантия.

#### Windows evidence и native boundary

Минимальная поддерживаемая Windows build 14393 подтверждена повторяемыми
прогонами с оговоркой, но не полностью доказана в exact CI условиях: прогоны
выполнялись с Python 3.13.2 и административными правами, а GitHub-hosted образ
Server 2016 отсутствует. Формулировка о доказательстве в exact условиях
применима только к проверенным hosted-сборкам.

`NtCreateFile` с `ObjectAttributes.RootDirectory` остаётся DDI/native boundary
через stdlib `ctypes`, а не стабильным Win32 API. Совместимость обеспечивается
runtime-проверками, exact CI на доступных Windows runners и fail-closed при
невозможности доказать закрепление.

**Уточнённая гарантия.** Поддельный токен не даёт право на рекурсивное
удаление; неподтверждённое непустое дерево не передаётся в рекурсивный обход;
корень и traversal закреплены descriptor/handle в принятой модели угроз. При
недоказуемом закреплении операция завершается fail closed, и допустим
остаточный `.pgw-quarantine-*`.

## ADR-45: политика атомарности и durability публикации manifest.json  [#45]

**Дата:** 2026-08-23. Дополняет ADR-12 (атомарность записи артефактов), не
заменяет его.

**Контекст.** ADR-12 и документация описывали атомарную публикацию
prepare-артефактов, но `save_manifest()` использовал прямой
`Path.write_text()`. `pipeline._write_atomic()` уже применял temp + rename для
`prompt.txt` и `route.json`, то есть манифест был единственным артефактом вне
этой схемы (аудит #42, issue #45).

**Решение.** Принята политика **atomic visibility only**: полная сериализация
JSON в строку до создания файла, `tempfile.mkstemp(dir=path.parent,
prefix=".manifest-", suffix=".tmp")`, единственное закрытие потока, публикация
одним `os.replace()`, best-effort удаление temp в `finally` без маскирования
первичной ошибки. При отказе `os.fdopen` сырой дескриптор закрывается явно.
`flush + os.fsync(fd)` и fsync каталога не выполняются.

**Обоснование.** Задача #45 — исключить наблюдаемый частичный или пустой
`manifest.json` и разрушение ранее валидного файла. Crash durability требует
отдельного кроссплатформенно обоснованного решения по fsync и в этот scope не
входит. Транзакционность всего набора артефактов потребовала бы
staging-каталога и rename каталога целиком — отвергнуто как расширение scope.

**Последствия.** Публичное API `save_manifest(entries, path) -> None`, JSON
format contract (`ensure_ascii=False`, `indent=2`, UTF-8, без завершающего
перевода строки, `newline` по умолчанию как у `Path.write_text()`), exception
contract (raw `OSError`), schema и версия манифеста не изменились. Порядок
публикации в `prepare_pipeline()` сохранён: `manifest.json` →
`manifest_sha256` → `prompt.txt` → `route.json`; завершающий маркер набора —
`route.json`, а не манифест. Коллизия «существует только `manifest.json`» при
`overwrite=False` остаётся открытой в #48: `os.replace()` по-прежнему заменяет
существующий манифест, preflight-проверки и смысл `overwrite` не изменены.
Тестов 331 → 351 (+20 failure-path и характеризационных), mypy 45 → 47 файлов.

**Статус:** действует.
