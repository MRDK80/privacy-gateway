# Реестр архитектурных решений (ADR)

Документ фиксирует принятые решения для Privacy Gateway после этапов Э1–Э6.
Формат: контекст → решение → обоснование → последствия → статус.

---

## ADR-01: Fernet как алгоритм шифрования

**Контекст.** Нужно шифровать исходные значения сущностей для хранения в манифесте. Требования: аутентифицированное шифрование, стандартная библиотека, простота.

**Решение.** Fernet (AES-128-CBC + HMAC-SHA256) из пакета `cryptography`.

**Обоснование.** Аутентифицированное шифрование — порча шифртекста детектируется немедленно. Fernet реализован в стандартной библиотеке `cryptography`, которая уже является зависимостью. Нет необходимости в собственной криптографии.

**Последствия.** Ключ — 32 байта в base64url. Манифесты зашифрованы конкретным ключом; при его смене старые манифесты нечитаемы без явной ротации (см. ADR-06).

**Статус:** действует.

## ADR-02: Ключ в системном keyring

**Контекст.** Fernet-ключ нужно где-то хранить между запусками. Файл на диске — ненадёжно. Переменная окружения — утечка в логи и историю.

**Решение.** Хранить ключ в системном keyring через библиотеку `keyring`. Service: `privacy-gateway`, Username: `fernet-key`. Байты ключа кодируются через `latin-1` для совместимости с keyring API (строки).

**Обоснование.** Системные хранилища (SecretService / macOS Keychain / Windows Credential Vault) предоставляют шифрование «из коробки» с привязкой к учётной записи пользователя.

**Последствия.** На headless Linux необходим `dbus-run-session + gnome-keyring-daemon`. В CI нужен mock или `PGW_KEYRING_BACKEND`. Backend валидируется по allowlist до любой операции (fail closed).

**Статус:** действует.

## ADR-03: Валидация backend keyring по allowlist

**Контекст.** Библиотека `keyring` может автоматически выбрать небезопасный backend (plaintext, in-memory) на headless системах.

**Решение.** Валидировать backend по полному имени класса (`module.qualname`) против allowlist: `SecretService.Keyring`, `macOS.Keyring`, `WinVaultKeyring`. Override через `PGW_KEYRING_BACKEND` также проходит валидацию. При несоответствии — `KeystoreError` до записи или чтения ключа.

**Обоснование.** Fail closed: лучше упасть с ошибкой, чем молча записать ключ в plaintext-хранилище.

**Последствия.** На неподдерживаемых системах или в CI без настройки операции с ключом не работают. Это намеренное поведение.

**Статус:** действует.

## ADR-04: Стабильность токенов — вариант A (per-document)

**Контекст.** Нужно определить область стабильности токенов: одинаковое значение (`user@example.com`) в одном документе должно получать один и тот же токен (`[EMAIL_1]`), но поведение между запусками не оговорено.

**Решение.** Вариант A: счётчик и словарь `seen` живут внутри одного документа (одного вызова `tokenize()`). Состояние между запусками не сохраняется.

**Обоснование.** Простейшая реализация. Манифест уже хранит все соответствия — сквозная стабильность не нужна для восстановления в рамках одного документа.

**Последствия.** `[EMAIL_1]` в двух разных запусках может соответствовать разным адресам. Важно при ручной обработке.

**Отложено:** вариант B (глобальный реестр токенов между запусками) — рассмотреть в Э7.

**Статус:** действует.

## ADR-05: Манифест хранит только token → encrypted_value

**Контекст.** Нужно определить, что именно хранится в файле манифеста.

**Решение.** Манифест содержит только: `token`, `entity_type`, `fingerprint`, `encrypted_value` (hex). Исходные значения в открытом виде отсутствуют. Ключ не записывается.

**Обоснование.** Файл манифеста может попасть в систему контроля версий или в резервную копию. Без ключа он бесполезен для злоумышленника.

**Последствия.** Для восстановления исходных значений необходим и манифест, и ключ из keyring.

**Статус:** действует.

## ADR-06: Ротация ключа делает старые манифесты нечитаемыми

**Контекст.** Необходимо описать поведение при смене ключа.

**Решение.** `MultiFernet` не реализован. При замене ключа `load_manifest` со старым ключом поднимает `DecryptionError`. Для ротации: 1) загрузить манифест со старым ключом, 2) пересохранить с новым.

**Обоснование.** Намеренная простота на текущем этапе. `MultiFernet` усложняет управление ключами.

**Последствия.** Пользователи должны явно ротировать манифесты при смене ключа. Риск потери данных при утере старого ключа.

**Отложено:** `MultiFernet` — Э8.

**Статус:** отложено (MultiFernet не реализован).

## ADR-07: Валидатор независим от детектора

**Контекст.** Валидатор (Э5) проверяет выход токенизатора. Можно было бы переиспользовать паттерны из `detector.py`.

**Решение.** Импорт `detector.py` в `validator.py` запрещён. Паттерны дублируются.

**Обоснование.** Асимметрия цены ошибки: ошибка детектора (пропуск) — валидатор поймает. Ошибка валидатора (пропуск) — утечка ПДн. Два независимых рубежа устраняют единую точку отказа. Детектор настроен на отзыв; валидатор — на точность с порогом энтропии 3.0 (vs ~3.5 у детектора).

**Последствия.** При изменении паттернов в `detector.py` нужно отдельно обновлять `validator.py`. Это намеренная стоимость независимости.

**Статус:** действует.

## ADR-08: Fail closed как сквозной принцип

**Контекст.** Во многих точках системы возможна неоднозначность: небезопасный keyring backend, неизвестный тип токена, повреждённый шифртекст.

**Решение.** При любой неоднозначности — безопасный исход: `KeystoreError` (keystore), `BLOCKED` / `PENDING` (validator), `DecryptionError` (crypto).

**Обоснование.** Цена ложной тревоги (ручная проверка) значительно ниже цены ложного OK (утечка ПДн).

**Последствия.** Пользователь будет видеть ошибки при нестандартных конфигурациях. Это намеренное поведение, а не баг.

**Статус:** действует.

## ADR-09: Стратегия токенизации вынесена в Protocol

**Контекст.** Поведение присвоения токенов (нумерация, область стабильности) может потребоваться заменить без изменения публичного API.

**Решение.** `TokenAssignmentStrategy` — Protocol с методом `assign(entity, value) -> str`. `PerDocumentStrategy` — дефолтная реализация (вариант A). Стратегия передаётся в `tokenize()` как параметр.

**Обоснование.** Позволяет подменить стратегию в тестах и в будущих этапах (вариант B) без изменения вызывающего кода.

**Последствия.** Стратегии можно тестировать изолированно. Вариант B (глобальный реестр) реализуем как отдельный класс.

**Статус:** действует.

## ADR-10: YAML-конфиг загружается только через yaml.safe_load  [Э6]

**Контекст.** Конфиг маршрутизации читается из файла, который может контролировать злоумышленник.

**Решение.** Единственный способ загрузки YAML в `routing.py` — `yaml.safe_load`. Использование `yaml.load` или `yaml.full_load` запрещено. Неизвестные ключи на верхнем уровне и в секции `rules` — явная `ConfigurationError`.

**Обоснование.** `yaml.load` с произвольными тегами (`!!python/object/apply`) позволяет выполнить произвольный код. `safe_load` отклоняет такие теги, что предотвращает deserialization-атаку.

**Последствия.** Конфиг с нестандартными YAML-тегами не будет загружен. Это намеренное ограничение.

**Статус:** действует.

## ADR-11: Конфиг не может отключить проверку секретов (fail closed)  [Э6]

**Контекст.** Конфиг маршрутизации позволяет задавать `block_unconditionally` и `tokenize`. Теоретически можно попытаться включить тип SECRET в `tokenize`, чтобы обойти блокировку.

**Решение.** Пересечение `tokenize_types` и `block_unconditionally` — явная `ConfigurationError`. Конфиг не может ослабить проверку безопасности.

**Обоснование.** Fail closed: конфигурационный файл — не привилегированный канал управления безопасностью. Безопасность не должна зависеть от корректности пользовательского конфига.

**Последствия.** Пользователи не могут случайно или намеренно настроить токенизацию типов, которые должны блокировать обработку.

**Статус:** действует.

## ADR-12: Артефакты создаются атомарно через временный файл  [Э6]

**Контекст.** При записи `prompt.txt` и `route.json` возможен сбой в середине записи, что оставит частично записанный файл.

**Решение.** Запись через `tempfile.mkstemp` в той же директории с последующим `Path.replace` (атомарный `rename` в пределах одной файловой системы).

**Обоснование.** `rename` атомарен на POSIX. На Windows атомарность гарантирована начиная с Python 3.3+ (`Path.replace`). Частично записанный файл недоступен читателю до завершения записи.

**Последствия.** Артефакты либо созданы полностью, либо не созданы вовсе. Нет промежуточного состояния.

**Статус:** действует.

## ADR-13: route.json содержит format_version  [Э6]

**Контекст.** Этап Э7 будет читать `route.json` для восстановления. Схема файла может меняться.

**Решение.** `route.json` содержит поле `format_version: "1.0"`. Значение константы `ROUTE_FORMAT_VERSION` определено в `pipeline.py`.

**Обоснование.** Явное версионирование формата позволяет Э7 и последующим этапам проверять совместимость и отклонять устаревшие файлы с понятным сообщением об ошибке.

**Последствия.** При изменении схемы `route.json` необходимо обновить версию и миграционную логику в Э7.

**Статус:** действует.

## ADR-14: Связывание route.json и manifest.json контрольной суммой

**Контекст.** Команда `pgw prepare` создаёт связанную пару артефактов: `route.json` содержит метаданные запуска и путь к `manifest.json`, а манифест содержит зашифрованные соответствия токенов исходным значениям. Формат `route.json` версии `1.0` не позволяет до начала восстановления определить, относится ли манифест к этому запуску, а также обнаружить повреждение файла манифеста целиком.

**Решение.** Поднять `format_version` файла `route.json` до `"1.1"` и добавить обязательное поле `manifest_sha256` — SHA-256 всех байтов финального `manifest.json` в виде 64 шестнадцатеричных символов нижнего регистра. Сначала `manifest.json` атомарно записывается на финальный путь, затем читаются байты этого финального файла и вычисляется контрольная сумма, после чего `route.json` с полученным значением атомарно записывается на диск.

Для проверки пары предоставляется публичная функция:

```python
def verify_manifest_integrity(
    route_data: dict,
    manifest_path: Path,
) -> None:
```

Для `format_version == "1.1"` функция требует поле `manifest_sha256`, вычисляет SHA-256 фактических байтов указанного манифеста и безопасно сравнивает значения. Несовпадение, отсутствие обязательного поля, отсутствие файла и неизвестная версия вызывают явную `ConfigurationError` с сообщением, не раскрывающим содержимое манифеста. Для версии `"1.0"` проверка пропускается ради обратной совместимости.

**Обоснование.** Контрольная сумма обеспечивает обнаружение рассинхронизации пары артефактов и повреждения файла манифеста до обработки его содержимого. Вычисление суммы после завершения атомарной записи гарантирует, что в `route.json` зафиксирован хеш именно финальных байтов файла, доступных последующему читателю.

**Ограничения.** SHA-256 без цифровой подписи или MAC не обеспечивает аутентичность и не является защитой от целенаправленной подмены. Субъект, способный заменить оба файла, может пересчитать контрольную сумму. Fernet отдельно аутентифицирует каждую зашифрованную запись манифеста; поле `manifest_sha256` не заменяет эту проверку и связывает только пару файлов целиком.

**Последствия.** Новые запуски `prepare` создают `route.json` версии `"1.1"` с обязательным полем `manifest_sha256`. Читатели должны принимать версию `"1.0"` без проверки контрольной суммы, проверять пару для версии `"1.1"` и явно отклонять неизвестные версии. Формат `manifest.json`, таблица кодов возврата и криптографическая схема не изменяются.

**Статус:** действует.

## ADR-15: Разрешение относительного manifest_path  [Э7]

**Контекст.** Команда `pgw restore` получает путь к `route.json` и должна найти соответствующий `manifest.json`. Поле `manifest_path` в `route.json` может быть относительным. Вопрос: относительно чего его разрешать — рабочего каталога или расположения самого `route.json`?

**Решение.** Относительный `manifest_path` разрешается относительно каталога, содержащего `route.json`, а не текущего рабочего каталога процесса. Абсолютный путь используется как есть. Явный флаг `--manifest` переопределяет путь из `route.json` и принимается в любом виде (абсолютный или относительный к рабочему каталогу). Проверка целостности (`verify_manifest_integrity`) проводится для фактически выбранного пути.

**Обоснование.** `route.json` и `manifest.json` создаются вместе командой `prepare` и физически находятся рядом. Разрешение относительно каталога `route.json` позволяет запускать `pgw restore` из произвольного рабочего каталога без необходимости менять `cd`. Это соответствует поведению большинства инструментов, работающих с конфигурационными файлами.

**Последствия.** Пара артефактов переносима: достаточно переместить директорию целиком. Флаг `--manifest` даёт явное управление для нестандартных сценариев.

**Статус:** действует.

## ADR-16: Строгий режим по умолчанию и семантика --lenient  [Э7]

**Контекст.** При восстановлении текста могут встретиться неизвестные или искажённые токены — токены, которых нет в манифесте либо которые не соответствуют формату `[TYPE_N]`. Нужно определить, как система должна реагировать по умолчанию.

**Решение.** Строгий режим включён по умолчанию (`strict=True`). В строгом режиме любой неизвестный или искажённый токен вызывает `RestoreError` с ненулевым кодом возврата (3). При строгом отказе результирующий файл не создаётся — `restored_text` возвращается как `None`. Мягкий режим включается только явным флагом `--lenient`. В мягком режиме неизвестные и искажённые кандидаты остаются в тексте без изменений и отражаются в предупреждениях. Отчёт в stderr никогда не содержит восстановленных (plaintext) значений — только счётчики и токены.

**Обоснование.** Fail closed (см. ADR-08): неизвестный токен в ответе LLM скорее свидетельствует о галлюцинации модели или манипуляции, чем о штатной ситуации. Безопаснее завершиться с ошибкой, чем молча передать частично восстановленный текст. Мягкий режим доступен, но требует явного opt-in.

**Последствия.** Пользователи, ожидающие частичного восстановления, должны явно передавать `--lenient`. CI-пайплайны по умолчанию получают строгое поведение без дополнительной настройки.

**Статус:** действует.

## ADR-17: Поведение при пропавших токенах  [Э7]

**Контекст.** Токен может присутствовать в манифесте (был создан на этапе `prepare`), но отсутствовать в ответе LLM. Это может означать, что модель законно исключила фрагмент текста или переформулировала его без использования токена.

**Решение.** Токен, присутствующий в манифесте, но не найденный ни в одном месте ответа LLM, считается пропавшим. Пропавший токен не является ошибкой сам по себе и не вызывает отказ ни в строгом, ни в мягком режиме. Пропавший токен обязательно включается в отчёт/предупреждение (`tokens_missing`). Пропавший токен не подставляется в произвольное место текста.

**Обоснование.** LLM может законно опустить часть текста. Принудительный сбой при пропавшем токене создал бы ложные срабатывания для нормальных сценариев суммаризации и переформулировки.

**Последствия.** Оператор может обнаружить пропавшие токены через отчёт и принять решение вручную. Автоматической компенсации нет.

**Статус:** действует.

## ADR-18: Поведение при дублированных токенах  [Э7]

**Контекст.** Один и тот же токен (например, `[EMAIL_1]`) может встретиться в ответе LLM несколько раз. Нужно определить, является ли это ошибкой и как обрабатывать подстановку.

**Решение.** Если известный токен встречается в ответе LLM более одного раза, значение подставляется во все его вхождения без исключения. Дублирование считается аномалией и фиксируется в отчёте (`tokens_duplicated`). Само по себе дублирование не вызывает отказ ни в строгом, ни в мягком режиме.

**Обоснование.** LLM может повторить токен при цитировании или перечислении. Отказ восстановления из-за дубля был бы чрезмерно строгим. Фиксация в отчёте позволяет оператору отследить нестандартное поведение модели.

**Последствия.** Результирующий текст будет содержать plaintext-значение во всех позициях, где встречался токен. Оператор видит счётчик дублей в отчёте.

**Статус:** действует.

## ADR-19: Регистрозависимость токенов  [Э7]

**Контекст.** Токены имеют формат `[TYPE_N]`, где TYPE записан заглавными буквами. LLM теоретически может вернуть токен в изменённом регистре, например `[email_1]` вместо `[EMAIL_1]`. Нужно определить, считать ли такие варианты эквивалентными.

**Решение.** Токены регистрозависимы. `[EMAIL_1]` и `[email_1]` не являются эквивалентными токенами. Вариант с изменённым или смешанным регистром классифицируется как искажённый кандидат (`tokens_malformed`), а не как известный или неизвестный токен. Автоматическая нормализация регистра запрещена.

**Обоснование.** Автоматическая нормализация регистра маскировала бы изменение токена в ответе LLM, что противоречит принципу fail closed (ADR-08). Изменение регистра токена — признак галлюцинации или манипуляции, который должен быть обнаружен.

**Последствия.** В строгом режиме токен с неверным регистром вызывает отказ с кодом 3. В мягком режиме он остаётся в тексте как есть и фиксируется в предупреждениях.

**Статус:** действует.

## ADR-20: Коды возврата команды restore  [Э7]

**Контекст.** Команда `pgw restore` может завершаться по нескольким причинам: успешное восстановление, различные категории ошибок. Нужно зафиксировать таблицу кодов возврата и её семантику.

**Решение.** Таблица кодов возврата (не изменяется в Э7):

| Результат restore | Код |
|---|---:|
| Успешное восстановление | 0 |
| Непредвиденная ошибка | 1 |
| PENDING | 2 |
| Ошибка входа, конфигурации, целостности либо строгий отказ по токенам | 3 |
| Ошибка keystore или отсутствие ключа | 4 |

Уточнения к коду 3: `ConfigurationError` от `verify_manifest_integrity` отображается в код 3; неизвестный или искажённый токен в строгом режиме (`RestoreError`) также приводит к коду 3. Уточнения к коду 4: отсутствие ключа в keyring (`KeyNotFoundError`) и любая ошибка keystore (`KeystoreError`) приводят к коду 4.

**Обоснование.** Значение кода 3 перегружено: оно объединяет ошибки конфигурации/целостности и строгий отказ по токенам. В Э7 таблица не меняется ради минимальности изменений публичного контракта. Разведение кода 3 на два отдельных кода готовится для Э8.

**Последствия.** Скрипты, анализирующие код возврата `pgw restore`, должны учитывать, что код 3 охватывает несколько семантически разных классов ошибок. Уточнение будет выполнено в Э8 без изменения существующих кодов.

**Отложено:** разведение кода 3 — Э8.

**Статус:** действует.
