# ADR-45: политика атомарности и durability публикации manifest.json

**Issue:** #45 (P0 Integrity) · **Источник:** аудит #42 · **Roadmap:** #49
**Дата:** 2026-08-23 · **Статус:** действует

Дополнение к `docs/DECISIONS.md` (ADR-12 «атомарная запись артефактов»).
Исторические ADR не переписываются: эта запись уточняет фактическую
гарантию для `manifest.json` и фиксирует границы обещаний.

## Контекст

`save_manifest()` публиковал документ прямым `Path.write_text()`.
Truncate + запись не атомарны, поэтому наблюдатель мог увидеть пустой
или частично записанный `manifest.json`, а отказ записи уничтожал ранее
валидный файл. `pipeline._write_atomic()` уже использовал temp + rename
для `prompt.txt` и `route.json`, то есть манифест был единственным
артефактом вне этой схемы — расхождение реализации с документацией.

## Решение

Выбрана политика **atomic visibility only**:

1. JSON сериализуется полностью до создания файла.
2. Временный файл создаётся через `tempfile.mkstemp()` в каталоге
   назначения (одна файловая система), префикс `.manifest-`,
   суффикс `.tmp`; фиксированные имена не используются.
3. Поток закрывается ровно один раз; при отказе `os.fdopen()` сырой
   descriptor закрывается явно.
4. Публикация — один `os.replace(tmp, manifest)`.
5. При любом неуспехе до успешного replace временный файл удаляется
   best-effort; ошибка `unlink` подавляется и не подменяет первичную.

`flush + os.fsync(fd)` и fsync каталога **не** выполняются.

## Что гарантируется

- Частичный или пустой `manifest.json` не наблюдается.
- При отказе serialization / mkstemp / fdopen / write / close / replace
  существующий манифест сохраняется побайтово, а при отсутствующем
  адресате новый файл не появляется.
- После успешного replace временный файл отсутствует, манифест —
  полный валидный JSON в прежнем формате.

## Что НЕ гарантируется

- **Crash durability.** Без fsync запись может не дойти до носителя при
  потере питания или панике ядра. Формулировка «crash durable»
  запрещена до отдельного решения по fsync (файл и каталог,
  кроссплатформенно обоснованно).
- **Транзакционность набора артефактов.** Атомарна публикация одного
  файла. При отказе после публикации манифеста `prompt.txt` и
  `route.json` могут отсутствовать; staging-каталог и rename всего
  набора в #45 не вводятся.
- **Абсолютное удаление temp.** Отказ самой ОС на `unlink` оставляет
  временный файл; это осознанный best-effort.

## Порядок публикации (подтверждён кодом)

Фактический порядок в `prepare_pipeline()` при статусе OK:

1. `manifest.json` — публикуется первым (затем `chmod 0600`, ошибка
   chmod подавляется на Windows);
2. `manifest_sha256` читается из уже опубликованного файла;
3. `prompt.txt` — `_write_atomic`;
4. `route.json` с `manifest_sha256` — `_write_atomic`.

Завершающий маркер набора — `route.json`, а не манифест: именно он
связывает набор через `manifest_sha256`. Предположение «манифест
публикуется последним» не подтвердилось и в #45 не насаждается;
порядок сохранён без изменений и закрыт характеризационными тестами.

## Совместимость

- Формат неизменен: `json.dumps(data, ensure_ascii=False, indent=2)`,
  UTF-8, без завершающего перевода строки; поток открывается с
  `newline` по умолчанию, как у `Path.write_text()`, поэтому байты
  файла не меняются ни на Linux, ни на Windows.
- Exception contract сохранён: ожидаемые отказы ввода-вывода уходят
  наружу как `OSError`; широкий перевод в `ConfigurationError` не
  вводится; cleanup ортогонален классификации ошибок.
- Публичное API `save_manifest(entries, path) -> None`, schema и
  версия манифеста не менялись.
- Права: `mkstemp` создаёт файл `0600`, публикуемый манифест не
  становится доступнее, `chmod` в pipeline сохранён.

## Граница с #48

Коллизия «существует только `manifest.json`» при `overwrite=False`
остаётся открытой в #48. `os.replace()` по-прежнему заменяет
существующий манифест — это ожидаемое временное состояние.
Preflight-проверки, смысл `overwrite` и их порядок не изменены;
поведение зафиксировано характеризационным тестом.
