# ADR303 supplement: original human final-owner source graph

Owner-approved design supplement to ADR303. Independent design review and explicit owner approval apply to the exact source contract below. Implementation readiness, installation, invocation, owner provisioning, runtime activation and final epic-to-main approval remain separate; none is implied by design approval.

ADR303 lines94–110 require an ORIGINAL OWNER-ONLY real-demo receipt and a separate trusted owner pin installation at the same OS-owner boundary as mandate installation. This proposal makes that original human confirmation concrete. It does NOT promise automated verification of physical events, cryptographic human identity, or protection from malicious processes with the owner's OS access. A human-authored original confirmation is distinct from a model/runtime success flag.

The existing three files remain approval.json (Approval2), approval-pin.json (Pin1), install-receipt.json (Receipt1). Add ONLY command-source.json (Command1) and final-demo-source.json (DemoSource1). Both are owner-only originals produced exclusively by the trusted explicit owner procedure below. No runtime writer, migration/copy/import, new runtime callback/flag or new autonomous operation exists. Missing all five files means owner wait; any partial/conflicting graph blocks.

## Exact trusted owner procedure and authority boundary

The separate trusted owner action is outside autonomous runtime and model sandbox, analogous to existing mandate installation. It is invoked only by the human owner after personally running/reviewing the real final demo against the exact candidate PR/head/base/checkset. The action receives the explicitly approved Approval2 digest and original human-authored DemoSource1 scenario/observations as direct human inputs, not issue/model/skill JSON, an autonomous callback, or a copied operator report. A pure shape check cannot distinguish these origins; this property is enforced by the already accepted external trusted-owner-action boundary, not invented runtime heuristics. Operational provenance admission is mandatory, not an assumed implementation detail. The owner operation is the fixed separate procedure ADR303_FINAL_OWNER_APPROVAL_V1 in the explicitly owner-approved pinned installation; its proposed fixed code address is installed-policy/tools/agent_owner_final_approve.py (future owner-only procedure, not an autonomous runtime entrypoint). Its bytes and supporting code must be included in the existing exact installation inventory and match the explicitly approved policy SHA and inventory digest, verified through the existing installation/policy validators. A worktree script, mutable PATH command, issue-provided procedure or otherwise unpinned executable is rejected. This names the future concrete code/source boundary; no such procedure is claimed implemented or installed now.

Before the human invokes it, the external trusted owner-operation boundary must establish all of: exact pinned installed code/inventory; direct human invocation with the exact explicitly approved Approval2 digest as the original argument; original owner-authored DemoSource1 input; fixed managed seed and launch identity; and the known model sandbox write-mount/transport exclusion for final-owner and the installation. The installed operation must independently revalidate the existing original runtime-adapter/fixed namespace command configuration and pinned code against the accepted model mount boundary; unknown or broader write reach blocks admission. Its output is the ORIGINAL existing Receipt1 at final-owner/install-receipt.json, which binds the original Command1 through owner_command_digest, exact approved digest/candidate/launch/owner/time, and Pin1 through installation_receipt_digest. No new receipt format, success flag, callback, approval service, signing key or runtime mandate privilege is introduced.

Direct human invocation and original receipt issuance are EXTERNAL OPERATIONAL prerequisites at the accepted owner-install/preseed boundary. During the existing trusted owner installation ceremony, the human/operator checks and records in its existing installation/handover record: the explicitly approved installed policy SHA/inventory, fixed owner procedure code address, managed seed/launch identity, actual fixed namespace/mount exclusion and absence of an autonomous writer/entrypoint, the directly approved digest/input, and resulting Command1/Receipt1/Pin1 digests. This is the operational record of what the human did, not an additional runtime attestation/source schema, receipt, token, launch field or approval boolean. No record supplied by candidate/runtime substitutes for that ceremony. Runtime does not read that handover to infer an otherwise unknown past human invocation.

Positive runtime acceptance is EXACTLY the following conjunction under the externally admitted writer invariant: (1) existing trusted installation/policy validators verify the fixed owner procedure and dependencies against approved pinned inventory; (2) fresh original launch/adapter and fixed namespace checks establish known exclusion of final-owner/installation from model write mounts and no approved autonomous owner-writer route; (3) fixed no-follow/private bounded reads validate the complete five closed originals, all acyclic digests/identities/times; (4) fresh original candidate/preparation/report, exact primary CI/current refs/children and original authority/control agree. Runtime proves source consistency of that retained graph, not a separate historical fact of human authorship or procedure execution. There is no sixth hidden provenance input, guessed history, caller trusted callback or runtime readiness flag.

Unknown EXTERNAL installation/ceremony readiness is deployment/readiness BLOCKED before this owner procedure or final-driver capability is used. No autonomous process may declare it ready, install the missing procedure or issue pin/zero. The operational record/check belongs to the existing human owner installation/handover ceremony, not a new on-demand approval service. Observable runtime mismatches (missing/unpinned procedure, unsafe original namespace/mount, missing/partial graph, changed source identities or authority) independently fail closed using the identified actual inputs. The future implementation must supply those deterministic existing-source checks; no such implementation/readiness is claimed now.

Two byte-identical five-file graphs with the same pinned installation and namespace inputs cannot be distinguished by runtime solely because one was copied by a malicious same-OS-owner process. That case remains outside the accepted threat boundary, as with mandate/preseed installation; this proposal does not add a rejection requirement or cryptographic guarantee for it. Known alternate/untrusted source paths or autonomous import/writer routes are forbidden where their actual path/code/mount evidence is observable. Mere command enum/private ownership/self hashes remain insufficient absent the admitted external installation/writer invariant and the complete runtime consistency checks.

No installation, invocation, action implementation, owner file write or activation is included here. The exact owner-only code address is a new proposed design binding requiring independent review and explicit owner approval before implementation; it creates no autonomous route to invoke that code.

The action independently reads managed launch/mandate, pinned policy, exact original candidate and primary PR CI/refs; compares full human inputs and canonical DemoSource1 digest against the explicitly approved Approval2 final_demo_digest; verifies owner/time/identity; then records the fixed Command1 procedure and exact explicitly approved digest, and installs the five-file graph with existing private file protections. It neither silently creates Approval2 from a runtime candidate nor accepts a runtime-approved boolean. Changed candidate/CI/ref/demo or digest mismatch stops installation. Do not overwrite a conflicting historical graph or repin an old approval to another candidate. A partial crash graph remains blocked; this proposal promises no cross-file transaction or stronger durability. A later explicit owner operation may resolve partial/conflicting state under reviewed procedure, never autonomous cleanup.

The original human procedure is the authority source for real-demo confirmation: it attests what the owner personally observed. Runtime independently verifies source provenance/private boundary, closed shapes and exact graph/current source links; it does NOT claim to re-enact or physically verify the human's observations. Existing #304 production scenario/runbook is not present in the candidate docs inspected; this closed embedded scenario/observation original is proposed instead of pretending an existing typed source exists. Owner may require particular scenarios as part of design approval; this draft does not claim any actual final demo was performed.

## Bounded sensitive-content and provenance tests

The trusted human owner procedure must review scenario/observation prose against the existing prohibition on retaining secrets/PII. Deterministic tests may use a finite explicit set of synthetic known prohibited sentinels (for example the literal fixture marker SYNTHETIC-OWNER-SECRET-DO-NOT-RETAIN), unexpected shape/path input, and the closed field/enum allowlists. Rejection of those known inputs is not certification that arbitrary prose contains no PII or secret; no universal detector or completeness claim is permitted. Runtime reports/errors/model payloads never export original scenario/observation/command content, including refusal cases; tests assert only bounded public facts/digests escape.

Provenance/consistency tests require the actual approved pinned owner procedure/inventory, original launch/adapter namespace inputs and complete current-bound five-file graph. They reject observable unpinned/mismatched procedure, worktree/PATH substitution, known alternate source/writer route, missing receipt, mismatched command/pin graph, writable model mount and missing/changed candidate/CI/authority. Operational tests/checklists for the EXTERNAL trusted ceremony cover direct human invocation/exact approved digest/input and actual output receipt, with unknown readiness blocked before use. These are separate from runtime graph tests; neither fixture booleans/mock verifier success nor a private handover claim grants runtime authority. Tests must NOT require runtime to distinguish same-OS-owner byte-identical copying, infer unknown human history, certify arbitrary prose, or physically verify the demonstration. No new attestation source, flag, callback or service is introduced.
